# Villages development

“Staging” means the Git/GitHub staging branch. The isolated Docker environment on port 8500 is “8500”; merging to staging and deploying to 8500 are separate outcomes.

- Optimize for simple, reliable development and low maintenance. Start with the smallest root-cause fix; reuse existing code and standard tools. Add permanent machinery only for a demonstrated problem with a clear net benefit. Remove replaced paths.
- Evaluate proposals candidly and explain concrete tradeoffs. Routine reversible engineering, testing, corrections, previews, and completed staging delivery are autonomous. Ask only for missing product decisions or authorization that materially affects the work.
- Before any audit, review, investigation or implementation that depends on current staging, fetch and verify `origin/staging`. Read-only work inspects that verified revision and identifies the inspected commit in findings. If fetching fails, explicitly report that freshness could not be verified and do not present cached code as current.
- Use one owned Codex worktree and branch from current staging and one PR to staging per logically cohesive change. Combine directly related or tightly coupled changes; keep independent fixes, infrastructure, policy and cleanup separate. Each PR should be independently testable, reviewable and mergeable where practical. A request, audit or workstream is an organizational grouping, not a PR boundary; avoid both unrelated accumulation and artificial fragmentation. Keep the chat and its review pointed at that worktree; changing a shell directory does not move the chat. Reuse it for feedback; preserve other tasks and unrelated dirty work. Inspect Git and the PR when resuming. Historical summaries and one-time implementation decisions do not establish permanent policy.
- Complete and merge independently deliverable changes through their applicable gates without waiting for the parent workstream. Record unrelated findings separately unless they prevent safe completion. Source merge, deployment to 8500, release and housekeeping are distinct outcomes; deferred deployment, Local synchronization and worktree archival do not block reporting a completed source delivery. Investigate other chats, checkouts or runtime problems only when concretely connected to the task.
- Commit messages and PR descriptions explain the final change, relevant validation and material limitations. Keep private preview URLs, checkpoint details and acceptance conversations in private runtime records or the originating chat. Update current documentation in place; remove superseded guidance instead of appending development diaries.
- Source is in packages/villages/src. Keep client/server privacy boundaries, server authority over Scenes/access/snapshots, request identities, revision checks, cancellation, retry accounting, and saved-world compatibility. Domain rules do not perform host I/O; features use explicit contracts. New Engine integration uses public APIs and declared permissions.
- Run static checks and explicit affected tests during iteration. CI runs the complete provider-free inventory on Linux and Windows for executable, configuration and ambiguous changes. The narrow instruction-only qualification in DEVELOPMENT.md retains required checks, reproducible builds, artifacts and package parity. Local feedback and mocked tests do not establish packaged or real-provider behavior. Never bypass required checks.
- Use one independent read-only technical reviewer for material saved-data, privacy/access, spending, recovery/concurrency, or architecture changes. Review a changed material assumption again; cosmetic edits need no review ceremony. Tests protect observable behavior and actual failure modes, not wording or implementation shape.
- Present a working isolated preview for significant new behavior and obtain the user's acceptance before staging. Routine copy/layout corrections and fixes restoring established behavior may proceed under standing authorization. Explicit staging approval with a small, specified addendum covers that addendum: implement it, verify it, and proceed without republishing the preview or seeking renewed acceptance. Require renewed preview and acceptance for material changes outside the approved scope or when the user requests them; a new package revision alone does not invalidate approval.
- Build generated output with the repository builder. Commit maintained source/tests/docs, not bundles or ZIPs. Preserve locked dependencies, pinned Engine declarations/runtime compatibility, reproducible archives, and immutable published bytes. Versions identify deliberate releases, not each development edit.
- Main promotion and numbered publication require explicit authorization. Upstream communications/contributions, deliberate paid model/gameplay requests, Engine source/build/upgrades, and personal Marinara operations require their separate authorization. Never use personal installations or data for development. Preserve explicit runtime pauses and unresolved recovery holds.
- Keep preview worlds independent. Never overwrite their progress implicitly. Checkpoint before consequential saved-data changes and retain rollback. New previews use a verified saved 8500 checkpoint without stopping 8500. Machine-specific runtime commands, credentials, and private data stay outside product Git.
- Product UI defaults to short labels, controls, values, and necessary results/errors. Remove redundant explanatory copy in touched areas; do not move it into help controls. Preserve user-authored content. Verify real layout on desktop and phone.

A Venue is the place; Zones are spaces within it. A Scene continues across Zone movement. Capture attendance, positions, activity, and time at its start; background changes cannot rewrite that active snapshot or expose unseen attendance.

Commands and release steps: DEVELOPMENT.md. Product behavior: packages/villages/README.md. Optional memories, archived procedures, and prior AI recommendations are context, not additional standing requirements. Model and thinking settings are managed by the user.

## Collaboration and engineering judgment

- Critically evaluate proposals rather than automatically agreeing or treating a suggested implementation as the best way to achieve the goal.
- Push back candidly when an idea is unsound, unnecessarily complex, difficult to maintain, or likely to cause future problems. Explain the tradeoffs plainly and propose a better approach. Distinguish established practice from personal preference.
- Ask for clarification when uncertainty materially affects the outcome. Respect the user's goals and final decisions while clearly flagging consequential risks.
