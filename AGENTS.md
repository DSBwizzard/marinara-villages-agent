# Villages coding guidance

- Villages source is under `packages/villages/src`: client entry/shell/features/shared, server entry/features/domain/adapters/jobs, and shared contracts/helpers. Read DEVELOPMENT.md for repository-owned commands and packages/villages/README.md for product behavior.
- Regenerate bundles, manifests, and checksums with the documented builder; do not hand-edit generated output.
- Normal builds use locked repository dependencies and pinned public declarations under `sources/engine-public`; they never copy or overwrite Engine source. Preserve provenance, license and documented API compatibility. The Decisions private adapter remains an explicit, identity-checked exception with fallback.
- Client code cannot import server implementation or private saved models. Shared contracts contain approved client-visible data. Domain rules cannot access storage, Engine, providers or timers. Connectors cannot call feature coordinators; feature coordination owns the work and depends on explicit services.
- Keep feature state alive for its intended draft, reading-position and pending-operation lifetime. Scene and snapshot authority stay on the server. Preserve request identities, revision checks, retry semantics and delayed-work fences.
- Local development and CI use `npm run check`, the test inventory, `npm run validate` and `npm run verify:build`. Identify mocked and Engine-dependent coverage accurately. Independent review is required for substantial architecture, saved data, privacy, recovery/concurrency or model-spending changes.
- Make focused atomic commits. Separate mechanical moves from behavior changes; explain the current behavior, proposed behavior, benefit and compatibility/cost impact before changing it. Commit maintained source, definitions, tests and documentation; generated output stays ignored.
- Versions identify deliberate releases, not each edit or staging commit. Distinguish staging builds and review iterations by source revision/content hash and archive hash. Freeze published package bytes; bump once for the next numbered release.
- Keep personal workflow tooling, reports, credentials, environments and machine-specific instructions outside product commits. Read any applicable local override. This repository does not authorize Engine source changes, upstream submission, publication or everyday restarts.

## Engineering judgment and discussion

- Treat user suggestions as goals to understand, not designs to accept automatically. If an approach creates a concrete risk to correctness, maintainability, privacy, recovery, provider spending, Engine integration or Git history, raise it before implementing the consequential part. Explain the affected behavior, evidence and tradeoff in plain language; propose the smallest practical alternative. Continue useful work that does not depend on that decision.
- Distinguish an enforced contract or authorization boundary from a design preference. Identify the relevant code, check, documentation or repository rule; do not invoke vague "best practice" as a veto. Verify uncertain host requirements against the supported Engine contract or authoritative documentation instead of inventing Marinara standards.
- Be open to deliberate exceptions. The user can choose different product tradeoffs after discussion, subject to applicable permissions and safety requirements. Record significant decisions and their scope, consequences and validation in maintained documentation. An agreed architectural change should update its contracts, checks and tests coherently, rather than disabling a failing gate to make a shortcut pass.
- Resolve routine, reversible implementation choices autonomously. Discuss changes that expand scope, alter externally visible behavior beyond the request, change data/privacy/spending policy, rewrite shared history, weaken validation or require Engine modifications. Do not repeatedly ask about a decision already authorized; report concrete blockers honestly.

## Sustainable development

- Villages is a Marinara Engine Agent. Prefer supported capability APIs, package permissions, lifecycle ownership and Engine services. Keep unavoidable private integration narrowly isolated and identity checked; discuss compatibility work before adding another private dependency or changing the supported runtime. Do not grow a separate host or duplicate Engine facilities without a demonstrated need and explicit scope discussion.
- Define observable acceptance criteria and identify the existing feature owner before implementation. Keep related state and effects together, collaborate through explicit contracts, and maintain client/server privacy boundaries. Add abstractions when they solve an evidenced problem; avoid speculative frameworks, parallel implementations and unrelated large refactors. Remove superseded paths within the reviewed scope.
- Test behavior and meaningful failure modes rather than implementation shape or test count. Keep coverage honest about mocked, Engine-dependent and real-provider tests. Choose proportional local validation, then complete the required publication checks. Review whether another developer can locate, understand and troubleshoot the changed behavior without tracing the whole application.
- Use an isolated checkout/branch for independent work; preserve other tasks' edits. Incorporate current staging before publication, inspect the complete diff, and use focused commits and a PR to staging. Respect required checks and applicable publication approval; never bypass protections, silently rewrite shared history or push directly to integration/release branches. Promotion to main is a separate decision. Keep secrets, personal data and private tooling out of Git, and regenerate package output with the builder.

## Scene continuity and access

- Venue is the place. Zones are dedicated spaces within a Venue, including Exterior, Common Space, and Private Space. A Scene is the active chat in one Venue and continues across Zone movement until it ends.
- Capture attendance, Zone positions, immediate activities, and scene time across the Venue when a Scene starts. Background agenda changes and resident movement must not mutate the active Scene. Only evidenced movement or departures within the Scene change its positions.
- Preserve Zone-specific witnesses and keep unseen Zone attendance server-only. Use current schedules when starting a new Scene. Preserve persisted identifiers and route compatibility when changing terminology.
