# Villages coding guidance

- Start independent work in an owned branch from current staging; reuse it for feedback and preserve other tasks. Keep commits and PRs focused. Main promotion and numbered publication require their own authorization.
- Read only the affected feature, contract and build inputs. Make the smallest workable root-cause change: reuse existing helpers and Engine services, prefer deletion to another abstraction, and avoid unrelated refactors. Explain consequential tradeoffs; resolve routine reversible choices autonomously.
- Source lives in packages/villages/src. Client code cannot import server implementations or private saved models. Domain rules cannot access storage, Engine, providers or timers. Feature collaboration uses the maintained public contracts; connectors do not call coordinators.
- Preserve server authority over Scenes, snapshots and access. Keep draft/reading/pending-operation state for its intended lifetime, including request IDs, revisions, retry semantics and delayed-work fences. Never expose unseen Zone attendance.
- A Venue is the place; Zones are spaces within it. A Scene continues across Zone movement. Capture attendance, positions, activity and time when it starts; background changes cannot mutate its active snapshot. Only evidenced movement/departure changes positions.
- Use supported public Engine APIs and declared package permissions. No private Engine imports. Keep compatibility/provenance accurate; pinned public declarations and public runtime exports do not authorize Engine changes or upgrades.
- Use npm run check:changed and affected tests/cases during iteration. Local feedback uses cheap owner/literal discovery; CI and local cache validity share the complete maintained input graph. Unknown inputs broaden coverage with a reason; reviewed runtime scopes in scripts/test-inputs.json are bound to exact source hashes and must be reviewed again after changes.
- Test observable behavior and meaningful failures. State-only fixtures need one width; real layout retains desktop/phone coverage. Do not add tests for trivial instructions or mirror implementation. Keep mocked, packaged, Engine and provider coverage distinct.
- CI owns complete Linux/Windows candidate coverage and prepared package identity. Reuse authenticated unchanged checks; do not repeat a full local inventory while CI validates that candidate. Trust-policy/toolchain changes require a new baseline. Never relabel focused coverage as complete.
- Use one independent read-only technical reviewer for material saved-data, privacy/access, spending, recovery/concurrency or substantial architecture changes. Start review before the expensive final baseline; resolve material findings. Cosmetic work needs no review ceremony.
- Build generated bundles, manifests, hashes and ZIPs with the owning builder. Commit maintained source/definitions/tests/docs; local generated outputs stay ignored. Versions identify deliberate releases; published bytes are immutable.
- Keep private workflow tools, personal features, credentials and machine data outside product commits. Upstream contributions follow docs/upstream-contribution.md and the upstream maintainer's current rules. This repository alone authorizes no upstream submission, paid testing or personal-installation operation.

Commands and architecture: DEVELOPMENT.md. Product behavior: packages/villages/README.md. Private environment/authorization policy stays outside product Git.
