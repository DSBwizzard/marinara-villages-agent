# Villages

## UI direction

The View Venue design is the current standard for new Villages UI work: deep navy backgrounds, layered blue panels, violet active states, large place imagery, clear area navigation, and readable details. Keep controls usable at desktop and phone sizes. Several selectable UI themes are planned for later; this language is the default until that work is designed and implemented.

Villages is a text-first slice-of-life sim for Home: a small village that follows device-local time, a handful of characters who go about exact daily schedules, and a noticeboard you can read when you stop in. You are a visitor rather than an avatar. When Marinara reopens, the village reconciles from its last saved instant and reconstructs the elapsed life you missed.

Current venue visits stay live for 30 minutes after the last deliberate input. Refresh restores a live visit; after inactivity the scene ends as **Interrupted: Inactivity** and Villages returns to the current map. Completed exchanges and verified effects remain in history, while a greeting-only visit is dropped. A reply may capture quiet, evidence-linked recollections for 24-hour continuity. When a played visit closes, one low-temperature System review adjudicates every recollection and promotes every distinct commitment, stable truth, meaningful preference or boundary, relationship change, or significant shared experience that deserves to last. There is no per-character or per-visit memory quota. A failed review never holds the room: the exact transcript stays archived and the review remains visibly retryable. Meaningful confirmed changes and newly durable memories appear once as dismissible star notices inside the venue scene. **DEBUG: Discard Visit** removes the active transcript without running durable review; already committed effects and passing recollections remain intact.

Find the package in **Agents → Download Agents**. Installation requires a restart: once installed and Marinara Engine restarts, **Villages** appears as a new tab in Home's browser shell. Uninstalling the package removes that tab and its routes after restart.

Villages is a first-class downloadable agent in the normal catalog channels. It remains under active development while this release is exercised.

## Venue projects

### Progress Engine foundation

The shared Progress Engine stores versioned task phases, typed evidence routes, separate disclosure, cited receipts, rejection reasons, and one-time resolution keys. It is model-free: task prose cannot prove completion. A saved visit is the replay outbox: Villages writes the turn first, applies typed evidence to Village state, then marks the turn processed. Startup recovery works through unprocessed turns in bounded background batches. The minute snapshot does not scan for progress or make a completion model call.

Newly founded villages use this engine for venue Projects. Existing villages keep their earlier Project path and are not migrated. Project phase receipts are canonical for new villages; stock debits, builder shifts, and venue opening remain Project actions in the same Village-state transaction. In the Project screen, **Record** selects an exact saved resident line for approval, builder agreement, a three-part checklist, a finite supply offer, or its handoff. Typed checks reject stale lines, absent speakers, wrong venues, conditional speech, unavailable stock, and reused proof. Selecting a supply source, delivering it, and beginning construction remain deliberate actions. Previously acquired supplies survive a builder or plan revision and can be explicitly committed to the new checklist. The debug-enabled **DEBUG: Progress** screen shows revisions, sources, rejected attempts, transitions, and turns awaiting replay. Hidden tasks stay out of the ordinary Project view.

If playtesting shows that reasonable social events repeatedly fail typed checks, explore a later, explicitly weaker evidence grade for model interpretation of cited scene lines. Such a grade must never authorize stock transfers, construction, or capabilities.

Projects has one New Venue slot and one Renovation slot. A New Venue begins with one Class, a name, and a description; place its generic blueprint on the Village map. It needs no village approval. A Renovation changes the physical form, Class, capacity, or one of a Venue's two reusable Upgrade slots. Residents and workers affected through that Venue approve in conversation or Mailbox before builder recruitment. Direct name, prose, picture, and Feature edits remain outside Projects.

The visible sequence is Concept and placement, affected-person approval when needed, Assign Builder, Define Requirements, Prepare Materials, 24-hour Construction, and Finishing Visit. Villagers explicitly agree to build during ordinary visits and appear as candidates. The chosen builder explains the structure materials, equipment, and finishing supplies, including anything unnecessary. The player accepts that checklist or asks the builder to revise it, obtains supplies in Village visits, and delivers them at the blueprint site. Construction follows the device-local clock across restarts and pauses if the builder leaves. The finished work remains a blueprint until the finishing visit opens it as a Venue. New Venues require a form and exterior and interior descriptions; pictures are optional. The Project screen has no embedded map or image panel: placement happens on the Village map and imagery belongs to the finishing visit.

Unfinished projects from the earlier receipt-based pipeline are retired when a saved village is upgraded. Completed Venues remain. A later pass will give each Zone its own visible Feature list.

## Venue editing and resident authority

**View Venue → Edit Venue** edits an existing venue's name, description, and pictures. New venues and map moves cannot be made through that editor after founding. An occupied villager Residence requires an invitation to enter its shared or private space. Once the player has entered, that space remains visible and its picture can be drawn, uploaded, replaced, or removed by the player. Edits to an occupied room's description or physical state become exact proposals. Every current resident approves a shared proposal; the owner approves a private proposal through evidenced spoken approval.

View Venue shows the exterior, class spaces, and private spaces the player has entered. Image controls live in Edit Venue. Exterior art appears on the map and outside scenes; an entered space uses its own image. The first visit to a private space starts one background image draw, while subsequent image actions are explicit player choices. A failed first draw never retries automatically.

A player can propose a move to an available venue. The villager accepts or refuses in conversation. A villager can also propose a move or one home-tier upgrade in conversation or during village life; the player decides in Venue Requests. An approved move completes after 24 elapsed hours, with a visible DEBUG shortcut. Occupied homes cannot be relocated, reassigned, converted, or removed until their resident moves out.

Residence entry and editing rely on explicit resident dialogue. A recorded invitation permits a one-use future visit; an invitation during a scene can admit the player immediately. Entry does not authorize changing furnishings or room state. A move archives the old private room and asks the System connection once to select portable personal elements for a new room. A failed adaptation leaves a retryable draft and the archive intact.

## Memory model

Villages keeps four deliberately separate layers:

1. **Live context** is the bounded recent scene history and recap used only while a visit is active.
2. **Passing recollections** are compact conversation events available to their exact witnesses for 24 real hours. They have separate subject and `knownBy` lists, exact visit/line evidence, and no player notification. An exact repeat reinforces the existing recollection and refreshes its expiry.
3. **Durable memories** are end-of-visit promotions in the chronicle. The System reviewer must decide every recollection, may consolidate several recollections into one event, and has no promotion quota. It promotes only commitments, stable personal facts, meaningful preferences or boundaries, relationship changes, and significant shared experiences not already represented by structured world state. Only promotions create star notices.
4. **Visit archives** are exact transcripts with line audiences. They are evidence and troubleshooting records, not character knowledge, and retention is configured independently.

Conversation memories are event-centric. A promise heard by four residents is one event with four knowers, not four competing copies. Subjects answer “who is this about?” and knowers answer “who may recall it?”; a knower is accepted only when they heard every cited line. Durable IDs are derived from the visit plus the sorted source-recollection IDs, so retries cannot create a second copy. The visit stores every promote/reject decision and reason before chronicle writes begin.

A played tiered visit is closed and releases the active-room pointer before review. No recollections means no review call. A failed or interrupted review leaves `memoryPending` with its transcript and decisions safely retryable; automatic retention skips it. Opening **Villagers → Memories** retries one pending review and shows passing context, durable history, archive health, and exact cited lines. Existing legacy chronicle entries remain untouched and use their older scope/actor fallback.

0.5.1 is the release where **founding is authoritative and adopted cards are durable snapshots**.

**A new village is founded in four deliberate steps.** Name the village and choose a Persona, choose separate System and Narration language connections, build the village, then review it before anything is written. The build step requires one player home, one to three Villager homes assigned to distinct Villagers, and one named public center placed on the map. System and Narration are both required and cannot share a connection. Images are disabled by default for a new village; players can leave them off, use the Engine default, or explicitly choose an image-generation connection. Image generation remains an explicit draw action. The resulting venue graph is the source of truth: later setup reads do not silently invent or replace homes and public places.

**Villagers keep the card they moved in with.** The complete adopted card is stored without `first_mes`, and ordinary runtime behavior reads that snapshot rather than falling back to the live library. Deleting a source card therefore does not erase a resident's identity, conversation, agenda, or village-owned routine. Records without a current snapshot are rejected rather than migrated.

**Refresh is explicit and reviewable.** The Villagers panel can preview the current library card, report when it is missing or changed, and apply a replacement snapshot deliberately. Each replacement increments its revision and clears agenda and schedule-remap derivatives so they are regenerated from the new card.

**The map and agendas follow the same contract.** Missing-card residents can still receive a Village-owned agenda without native schedule input, and map pins expose their place and occupant clearly to assistive technology. This release requires the generated package to be rebuilt and catalog metadata to be regenerated.

0.5.0 is the release where **places become durable venues instead of a pair of special lists**.

**Every place now has one stable identity.** Homes and public places share the same venue record, with nested presentation, occupancy, capabilities, and state fields. Rooms, images, schedule translations, and historical venue events refer to that stable venue ID, so renaming or editing a venue does not move its history to a different place. Older records are read through the new shape without inventing identities for obsolete venue data.

**Venues can be managed safely.** The package exposes venue creation, editing, image management, deletion previews, and deletion cleanup. Removing a venue clears its room and image dependencies while preserving historical event records with the venue's former name and ID. A residence change is proposed and approved separately, so a character cannot be silently moved by an ordinary venue edit.

**The client follows the same contract.** The map, venue panels, room navigation, schedule display, and event history use nested venue data and stable IDs throughout. Installing it still requires an Engine restart.

0.4.74 is the release where **a failed chat can be retried without duplicating the player's message**.

**A network failure used to make a retry ambiguous.** The first request could have reached the model and written the turn before the response was lost, while the client had no identity to carry into the retry. Pressing Send again then looked like a new turn, so the model could answer twice and the transcript could contain duplicate player lines.

**Every private and room send now carries a submission receipt.** The client keeps one ID for the logical send and reuses it after an uncertain failure. Villages reserves that ID before calling the model, commits the receipt with the durable server-issued line IDs, and replays the committed result when the same payload arrives again. Reusing an ID for different content is rejected, and a generation failure releases the pending receipt without writing generated content. Room commits are atomic, then mirror the exact committed lines into participant transcripts without duplicating repaired copies.

This is a Villages retry contract, not ordinary Marinara Engine route idempotency: the extension is implemented by this package and only applies when the client supplies a submission ID. No new permission, dependency, or Engine version is required, and older stored transcripts and rooms read with empty receipt lists.

0.4.73 is the release where **the schedules panel is the Engine's own week**, seven days deep and pressable, with each resident behind their own disclosure.

**Three complaints, one cause.** The panel showed a **window of three days** beginning today — the Engine keeps seven, and a window is the panel deciding which of somebody's days are worth looking at. It stacked every villager's week on top of the last, so a reader who came for one person scrolled past the whole village to reach them. And it printed an hour's facts as one unlabelled run of text, so the two things this panel exists to compare could not be told apart. All three are the same mistake in different clothes: the panel had its own idea of what an hour is instead of drawing the Engine's.

**So it draws the Engine's week, at the Engine's own scale.** Seven tracks per resident, one per day, in order and beginning with today, each labelled with the Engine's weekday and the village's own date for **that occurrence of it** — the Engine's week holds no dates at all, so the two are joined in the panel and nowhere else. A day the Engine has nothing for keeps its track and says so, because a blank row is a fact about the card and a missing row is the panel losing one; a villager with no week at all gets seven of those, which is a blank schedule rather than a gap.

**Every hour is a press, and it opens exactly two labelled lines.** The block geometry is the Engine's schedule editor's to the pixel, including its floor on a block's width, so a player who has seen that screen does not have to read a second, differently-shaped account of the same week to check it. Pressing a block opens `Schedule event:` — the Engine's own line, copied off the character card and never touched — and `Agenda event:`, the same hour in the village's own terms, which is what every prompt downstream actually reads. The two are labelled because they are two different answers to one question, and a reader who cannot tell which is which cannot tell a translation they disagree with from the schedule it was made from.

**Everything else about the hour rides in a caption beside the bubble:** the availability token, whether the clock is in it, and whether the village had words for it at all. A third kind of statement inside the bubble would ask a reader to sort two kinds of claim apart on the one row that has to be unambiguous, and none of those is a second answer about the hour. That caption is also where 0.4.72's wish moved to — the wish that bent an hour was printed under the agenda line, and it is not what the hour **reads as**, it is a note about how it came to read that way. Which wish bent what is unchanged: the same id, resolved at the same moment, naming the same hour in the same panel.

**A night is drawn as the two pieces it really is.** An hour that ends before it starts is one block crossing midnight, so it is drawn at the right-hand edge of its own day's track **and** at the left-hand edge of the same track, both pieces the same press, the second carrying no name because the hour was announced by the first. An hour with no place on a clock — the Engine's own `whenever`, or a typo — is not dropped either: a range that cannot be read has no position on a track, and dropping it would be this panel quietly shortening somebody's day, so those hours are listed under their day, still pressable, still two lines when opened.

**Each resident is a disclosure, and shut.** Shut, the panel is a list of names with their state beside them — the missing card, the week's start date, whether the translation is out of date, and the count of hours the village has no words for — which is the question a reader arrives with; open, it is the whole week. It is a native `details` rather than a press this package animates, because the browser already knows how to open one from a keyboard, how to announce it as expanded, and how to leave one open for a reader coming back to it. Escape closes the opened hour and nothing else, handled on the resident's own body rather than on the document, so a reader who pressed Escape at a bubble does not also shut the surface behind it.

**Nothing is written by any of this.** No stored field is added, no prompt changes and no model call is spent, and `engine.min` does not move. The change has a **server** half — the week view now answers with all seven days instead of a three-day window — so installing it needs a restart, like every release. `tests/villages-village-chat.regression.ts` holds the seven-day window (seven days in order, today first, each weekday once, seven distinct dates, and a villager with no week getting seven empty ones), and `tests/villages-schedule-remap.regression.ts` holds the panel itself (both labelled lines present and in that order, both inside the resident's own disclosure and behind no second press, the wish resolved from the id rather than stored as a name, and the wish drawn in the caption beside the bubble rather than as a third line inside it). All sixteen suites, `npm run check` and all three catalog gates pass.

0.4.72 is the release where **you can see what a wish is doing**, and where the tab says outright why one obvious press is not there.

**A wish is invisible by design, and that made it uncheckable.** Nothing a villager wishes for is ever said out loud, nothing about it reaches a prompt as a fact, and the only trace it leaves is its consequence — an hour that reads differently from the routine it came from. The debug tab is therefore not a convenience here, it is the only place a wish can be looked at at all, and it was showing the wrong half of it. The one failure this display exists to catch is a translation that tags a move with a wish whose phrase plainly has nothing to do with it, and catching that needs the wish and the hour it bent **on one row**.

**Every wish now says how old it is, and when it dies.** A wish reads `written today`, `written yesterday` or `written N days ago`, and then either `dies 12 Oct` or `never dies`. The two dates are the one thing about a wish that cannot be worked out afterwards — a wish that vanishes between two visits is a bug until the day it was always going to vanish on is printed beside it — and a wish whose dates cannot be read, which is every wish written before 0.4.71, says **never dies** rather than naming a day nobody wrote. That line is worked out from the store the tab has just read rather than from a timer of its own, so it cannot drift out of step with the clock the rest of the tab draws.

**Every hour now says which wish bent it, by name.** The tab resolves the id the translation stored against the wishes that villager is holding **at the moment the row is drawn**, rather than keeping a name beside the hour: a wish that has since been settled, lapsed or aged out is gone from the list, and a stored name would go on claiming that something which no longer exists bent that hour. An hour no wish bent prints nothing beside it, and that empty half is load-bearing rather than incidental — an untagged hour must not inherit the wish above it, and a week written before this release reads exactly like a week no wish has touched. The id is copied out onto the hour on the server side rather than looked up from the move the hour came from, because what the hour **reads as** is a question the translation already answered, and a second lookup would be a second answer to it.

**And the press that is not there is now said out loud.** A "send somebody there now" control cannot exist honestly once a wish holds no place: where a villager goes is the translator's decision, and a button that moved one would be the player's wish wearing theirs. The tab says so rather than leaving the gap to be read as unfinished, and says what the press it **does** have now means — forgetting a translation throws away the village's reading of that week, and the next one is written from the wishes as they stand then, so a wish answered since stops bending anything and a wish that arrived since starts.

**Nothing is written by any of this.** No stored field is added, no prompt changes and no model call is spent; the two dates have existed since 0.4.71 and are simply drawn now. The one server-side change is that the day plan copies a move's `wishId` out onto the hour it drew, so the client has something to resolve it against — which does mean installing this needs a restart, like every release. `tests/villages-schedule-remap.regression.ts` asserts which wish bent which hour, empty half included, and asserts that the age line is drawn on the wishes panel, that a deadline which cannot be read never expires, and that the sentence about the missing press is still there. All sixteen suites, `npm run check` and all three catalog gates pass.

0.4.71 is the release where **a wish is something a villager can lose**, and where the whole vocabulary of them is finally called what it is.

**A wish used to be permanent, and that was the wrong shape for it.** A villager's list had exactly one way out and the player owned it: settle the thing, and the village helps them put it down. Everything else stayed on the list for the life of the village, so a wish that had become impossible in the fiction — and one everybody involved had simply moved on from — went on bending hours and colouring prompts for as long as the village existed. Two of the three ways a wish actually leaves a person's mind were missing, and neither of them happens because the player did anything.

**The first is a lapse, and only the narrator can notice it.** The reply that writes a part of the day now carries a fourth list beside the happenings, the memories and the notices: `lapsed`, whose entries name a resident and quote one of their wishes **word for word**. It is the one thing a reply can say that takes something away, so it is the only part of a reply that is checked **twice over** — the name has to be a resident the village holds **and** the words have to be a wish that resident is carrying, in full. A near miss is refused rather than repaired, because a wish quoted in full is a different wish the moment a letter changes; a stranger's name is refused, somebody else's wish in the wrong mouth is refused, and the safe direction to be wrong in is to let a wish run its course. **Up to three lapses** are taken from one reply and the rest of it is written as usual, and **a lapse is a line in one list and nothing else**: never a happening, never a memory, never a notice, and never somebody announcing that they have given up on something. The prompt says all of that outright, and says that an empty list is the ordinary answer.

**The second is the clock.** Every wish is stamped when it is written with the moment it was born and the moment it dies, and the deadline is **rolled once from the wish's own id** — one to seven days, three parts in four of them inside three — so it needs no stored copy of itself, survives a rebuild and a read-back unchanged, and is never derived a second time. **A villager is never told about it**: nothing in any prompt says a wish is running out, because nobody knows that about themselves and a wish with a countdown is a quest with a timer on it. It is taken off the record on the part of the day that passes it, **before** the week is translated, and that order is load-bearing rather than tidy: a wish is part of what a translation is written from **and** part of what says a written one is stale, so a dead wish left on the list would bend hours around something nobody is carrying any more and file the answer under a signature the very next part of the day disagrees with. A wish whose dates cannot be read — everything written before this release — has **no deadline at all** rather than a guessed one, and never expires.

**And losing one asks for another.** This is the one place in the package where losing something spends a model call: a villager left short is asked what they want next, in the same breath as the part of day that took the wish away, with the dead wish's own words handed over as the thing not to wish for again. It is capped at **two per part of day**, because a roster written in one afternoon loses a whole village's worth of wishes on the same day and one part of a day is not allowed to answer that with sixty calls — whoever is left over is asked on the next one. That pass spends its calls **above both switches**, which is the one counter-intuitive thing in the release: a part of day the player has switched off still ages wishes, and the list of who lost one is the only copy that will ever exist, so a tick that returns early must not throw it away unanswered.

**Three ways out, one record, and nothing downstream has to care which one happened.** A wish leaves because the player settled it, because the narrator lapsed it, or because its day came. All three end in the same place — a shorter list — which is a shape the whole package already reads: the tab, the villager's own prompt, the judge's numbered list, and the hours the translation bends.

**And a wish is now called a wish everywhere.** The package's own modules, types and prompts were split between "want" and "wish" for as long as the second half was being built; 0.4.71 finishes the rename. The debug tab is **Villager Wishes** and the macro is `{{wishes}}`, which is what the presets have been rendering since the wish work landed. Nothing the village says, stores or decides about a wish changed with the words.

**What it costs.** A wish entering or leaving a villager's list changes that villager's translation of the week: a wish is quoted in the prompt that writes it, and an answer that mentions one is not interchangeable with an answer that does not. That is **one model call for that villager** on the next part of the day, not one for the village, and it is the price of a translation that knows what the week is being lived for. Two more stored fields ride on each wish — the two dates — so this release does add to what is on disk; a village founded before it reads exactly as it did, because its wishes have neither date and therefore never expire.

Installing 0.4.71 needs a restart, like every release, because the change has a **server** half. No new permission is asked for, no new dependency, no new file, and `engine.min` does not move: the dates ride on a wish the village already stores and the lapse list rides on a reply it already reads.

**And the shape is asserted rather than remembered.** `tests/villages-village-chat.regression.ts` drives the lapse list through the real route with fourteen entries at once — a padded name, a stranger, somebody else's wish in the wrong mouth, a wish off by one letter, a duplicate, an empty wish, a number where a name goes, a missing field, and three shapes that are not entries at all — and requires that a malformed entry costs nothing, that a repeat spends no slot of its own, that a near miss can never be repaired into a match, that exactly **three** come off one reply and which three they are, that the day is still written up as usual, and that nothing about a lapse appears anywhere in the news, the noticeboard or the chronicle. It then ages wishes out through the clock and requires the week to be retranslated and the replacements asked for — capped at two, with the third villager left for the next part of the day — requires the same on a part of the day nobody is writing up, and requires the reply's shape and its rules to be absent **entirely** from a village where nobody is holding anything. All sixteen suites, `npm run check` and all three catalog gates pass.

0.4.70 is the release where **the third debug press opens the menu it lives on**, and where the client tree is put through a compiler so that the next mistake like it is caught before it ships.

**0.4.69 moved the press into the chat and blanked the tab.** The press calls a prop, and the prop was declared and handed over and never taken — a prop that is declared and not destructured is not a prop at all, so the name was bound nowhere and the render threw the instant the "..." menu opened. React unmounted the tree and the whole tab went black, every control on it with it. All fifteen suites, `npm run check` and all three catalog gates passed it: the bundle is built with no type pass, ESLint's `no-undef` is off for TypeScript, and a suite that reads source as text cannot tell a name that is written from a name that is bound. The fix is one missing word.

**And the gap that let it through is closed.** `tests/villages-client-scope.regression.ts` runs the TypeScript that `npm run check` already has on disk over all three files of the tab's client tree, and fails on the diagnostics that mean a file is wrong on its own terms — a name that resolves to nothing, a prop the type requires and the caller never hands over, a binding read before it exists. React is not installed in this repository, so the unresolved-module complaints that come with that are expected and are counted rather than asserted on; everything else is a defect. The suite proves its own instrument armed before it checks anything, and it was watched failing on this exact bug, naming the line, before the word was put back.

0.4.69 is the release where **the press that forces a villager's ending is in the chat, where it is wanted**.

**0.4.68 put it on the debug panel, and that was the wrong room.** The press acts on **one** conversation, and the panel could only reach it by opening a room first — a navigation step for a press about the villager standing in front of you — so it was never where anybody looked for it. It is in the conversation's own **DEBUG** menu now, under the "..." beside _Close chat_ and _Force end chat_, and it is named for what it does rather than for what it achieves: **DEBUG: Force character-triggered chat end**.

**Nothing about the press itself changed.** The same flag, the same waiting, the same forced line, and the same road under it: a real line into the room that is already open, the model's own answer carrying the marker, the line held as the last thing they said, and the conversation filed by the same `/end` the player's own goodbye uses. It is shut until the villager has actually said hello, because a room with no hello in it has nobody to end anything. The panel's paragraph about it went with it, and the panel keeps the press that rewrites an agenda, which is the one thing only it can do.

0.4.68 is the release where **a villager can end the conversation themselves**.

**Until now every conversation in the village ended one way: you said goodbye.** A villager could walk out of a room and a room could be closed, but a private word with one of them ran until the player stopped it — which is not how talking to somebody works. People leave. The ones who leave are usually the ones with somewhere to be, and until this release the village had no way of saying so.

**So the turn carries a permission rather than a rule.** An ordinary chat turn — **not** a question being answered, **not** a claim the village has just ruled on, **not** a goodbye being written, and **not** a room — is told that it **may** end the conversation, and told in the same breath that it rarely should: only when the talk has genuinely run out **and** there is somewhere else to be, never as a way past an awkward pause, and that a lull is not an ending. Most turns are not this one, and the wording says so. Nothing counts turns and nothing rolls a die — the frequency control is the writing, because a threshold guessed before the wording is known to be wrong is a threshold guessed at.

**A villager who means it says a line of their own and writes a marker at the very end of the answer.** What they say is a sentence about their own day or about seeing you again; the marker is what makes it an ending. **It is the whole of it** — nothing else ends a conversation, so nothing ends by accident and nothing ends without it. A marker anywhere but the last line is ignored, which is the safe direction: a villager who says "that is all I have to say" and then keeps talking has ended nothing.

**And it is read before anything else touches the answer.** Once, at the top of the reader, before the reply is split into the beats the card is drawn from — and taken out before anything is stored, so the marker never reaches the transcript, the paragraph reader, the VN card, or a room. It is the wire format rather than a promise, which is why the marker is the one thing in the prompt shown to the model in full.

**What happens next is the ending the tab already had.** The conversation route answers with the conversation and **one flag** on it, and the drawer runs the tail the **End** button runs — the walk out, the filing, the snapshot — with the one part of it that is the player's taken out, because there is nobody to say goodbye. The line they finished on is held up in place of the conversation, exactly as your own goodbye is, and the drawer says **which of the two happened** rather than telling you that you said goodbye when you did not.

**A room is left alone on purpose.** A villager saying goodbye to a room does not end the room and does not close their own copy of it; the marker is stripped there and otherwise ignored. Who ends a **room** is a question for another release, and the code says so where it happens.

**And the one thing a test cannot decide has a press.** Whether a villager ever chooses to walk out is a model's decision, so the conversation's own **DEBUG** menu — the one under the "..." in the chat, beside Close chat and Force end chat — carries **DEBUG: Force character-triggered chat end**: it says one short line into the room that is already open and has them end it through the road above — the marker, the flag, the ending, the filing, with no branch for the press. It is shut until the villager has actually said hello, because a room with no hello in it has nobody to end anything. What it proves is that the road is joined up end to end. What it cannot prove is that a villager would ever choose to walk it.

**The suite holds the wording and the gates, because the decision is the one part it cannot hold.** `tests/villages-village-chat.regression.ts` drives the reader directly — a marker at the end counts and is removed, a marker anywhere else is stripped and ignored, a line that merely contains the marker is untouched prose — and then holds the permission against the turns it must never be offered to: an ask, a claim already ruled on, and a goodbye. It also forces an ending through the real road and requires the stored line to be the villager's own words with the marker already gone.

Installing 0.4.68 needs a restart, like every release, because the change has a **server** half. No new permissions are asked for, no new dependency, no new file, no new stored field, and `engine.min` does not move: a villager's own ending is written with the same two pieces the player's goodbye is, and a village founded before this release reads exactly as it did.

0.4.67 is the release where **a crowd is a room you can walk into**.

**A place with several people in it used to be the one press the map could not answer.** The place screen listed them and said in as many words that talking to more than one at once was not built, so the player picked, one at a time. This release is the **room**: everybody standing there when the player walked in, in one conversation, each of them keeping their own copy of it. The sentence on the place screen is gone, because it is no longer true.

**A room is one conversation _at a place_ rather than a second thing per villager.** It is kept by the place and it belongs to the village, so **walking into a place nobody has walked into before costs no model call at all** — the drawer opens on the names, the picture, and an empty room, and nobody is asked to greet you. It draws itself over the village's own picture of the place, and a room closed on the map is read back where it was left. Who is **in** it is frozen on the first line the player says: the hour can turn mid-conversation, and the cast must not turn with it.

**Who answers is a setting**, because there are two honest ways to run a room and the only way to choose between them is to try both. **Each of them answers** — the default — is one call per villager standing there, each asked for a reply of their own, drawn in the order the village lists them. **The room answers** is one call for the whole turn, answered as the room they are standing in rather than as anybody in it, and read into a line per speaker. Four villagers in one room is **four calls one way and one call the other**. The toggle sits in Conversation settings beside the preset and the reply length, and says which is which.

**Every participant keeps their own copy.** What is said in a room is written into each participant's own conversation as something they **heard** rather than something they said, so a room is not a second memory a villager has to be reconciled with their first, and their next private word starts from the room they were just in. Ending the room ends each of those copies through the same reader a private conversation ends through — and if one of them cannot put it into their own words, the room is kept whole to end again rather than left half-closed.

**On the map, a crowd is a fork in the road too.** A place with more than one person standing in it now offers the same two doors a house does: **About** for the place, **Enter** for the room. The place screen leads into the same room by one button under the names — _Talk to all 3 of them_ — and both presses hand the tab back to the map, where the drawer lives, exactly as the villager list has always done it.

**Pulling somebody aside out of a room is not in this release.** Asking one person in the room a private question, with the room still standing, is the next thing a room wants and it is deliberately not here yet — the room's own sentence in the settings says what it does and nothing more.

**And the shape is asserted rather than remembered.** `tests/villages-group-chat.regression.ts` covers the room's own reading — a room-answered turn split into a line per speaker, a line inherited by whoever did not get one, the cast frozen on the first write — and `villages-homepage-layout`, `villages-markdown` and `villages-speech-shape` were re-anchored where the room is a **second drawer** drawing the same furniture: the same paragraph reader, the same band of asides, the same described beat naming its own register. Nothing was loosened; every count that moved now says which of the two drawers it is counting.

Installing 0.4.67 needs a restart, like every release — and the restart is not optional this time, because the room has a **server** half. No new permissions are asked for, no new dependency, no new stored field that anything already on disk has to be read into, and `engine.min` does not move: a room is a document in a table the package already owns, and a village founded before this release reads exactly as it did.

0.4.66 is the release where **every house offers the same two doors, the one you live in included**.

**0.4.65 offered the choice, but not to your own house.** The two doors — About and Enter — were offered to a pin with exactly one villager behind it, and nothing is ever standing in the player's house: a villager's hour that names nowhere resolves to their own address and never to somebody else's. So the house a player looks at most often was the one house on the map that decided for them. It is a house like the house next door, so it is offered the same choice for the same reason — a house is somewhere to look at or somewhere to walk into, and an empty one is still both.

**The two doors now mean two different things on every house.** **About** opens the place screen **with the About panel already showing** — the note, what stands there, and the setting — which is what a player asking about a house is asking for. **Enter** means going in: a house with somebody in it meets you with them, an empty one gives you the room and _You have the place to yourself._ Before this, About was the plain place screen, which is not what the word promised.

**And the question is one reader.** `pinHasDoors` is asked both by the pin that draws the doors and by the press that decides whether to offer them, so a pin can never draw a choice the press would not offer, or the other way round. A house offers both doors whether or not anybody is standing in it; a place with exactly one person in it offers both, as before; everywhere else — an empty mill, a crowd — the press still means one thing and goes straight to the place screen.

**Nothing about the player's house is a special case.** There is one place list and one way in; the house the player lives in reaches the same doors through the same predicate as every other house, because it is a house.

Installing 0.4.66 needs a restart, like every release. No new permissions are asked for, no new dependency, no new file, no new stored field, and `engine.min` does not move. Nothing already on disk is rewritten or dropped, and a village founded before it reads exactly as it did — what changed is only what a pin offers when it is pressed, which is drawn afresh every time.

0.4.65 is the release where **a house is named after whoever lives in it, and a place with somebody behind it asks you what you meant**. Both are the map answering a question nobody had asked.

**The pins named houses after their buildings.** Every house in a village is a small home, so every house pin on one picture read _Small home_ — four pins, one word, and no way to tell whose door was whose. A village does not name its houses; everybody knows where everybody lives. So a house is named after its resident now: **Professor Mari's house**, and **Empty house** for one nobody has moved into, which is the one fact a player looking for a house is actually looking for. The player's own house is named by **the same rule** out of the Persona — _Sable's house_ — rather than by one of its own, because the player lives in a house like everybody else does and the day they can move, the map has nothing new to learn. At the end of the look-around you get _You are standing in Professor Mari's house_, out of the same two readers, so a pin and the screen it opens can never say two things about one house.

**A pin with somebody behind it opens a choice rather than their conversation.** In 0.4.64 a pin with exactly one villager standing in it went straight into that conversation, which is tidy right up until the moment you wanted to know what kind of house this is and were answered with a greeting. Pressing that pin now opens **two doors on the map** — **About**, which is the place screen, and **Enter**, which is the conversation. The choice belongs to the pin: it opens under the pin you pressed, and pressing the picture anywhere else, or another pin, is the way out of it. 0.4.61 is the release where **a translation that failed says so, and where the village stops calling it "saying"**. **Four faults, and each of them was enough on its own.** The refresh ran **below** the tick's own reasons to stop early, under a comment claiming the opposite — so on a tick that had nothing new to report, which is most of them, the village returned before it ever got to a translation. The button is now **Forget this translation**, and it is offered only once there is a translation to forget; the wording is _translated_, _translation_ and _no words for_ throughout the tab, the prompts and the route comments. 0.4.60 is the release where **the schedules tab shows the week again**, because the village's own reading of it stopped being a glossary and became a **timetable**. The listing was there and the tab drew almost nothing for it, which is what got reported. Underneath that was the real fault: the village's reading of a week was keyed by the **activity sentence**, so a week with five copies of _sleeping_ in it had **one** entry answering for all five, and all the tab could print was that entry once with the hours summed — _50h a week_. Every hour of the week collapsed into a handful of distinct sentences, and a player who wanted to check one hour of one day against their card could not check anything at all.

A sentence cannot be shared, which is the whole of the fix.

**That changes what the tab is.** Every block of the next three days is now printed **twice**, side by side and labelled. `Schedule event:` is the hour and the sentence exactly as they sit on the character's card, and `Agenda event:` is this village's phrase for that hour and the place it happens in. The ingested week is **copied** to make the second line rather than edited, which is what makes the pair worth reading: you can hold the village's reading against the card it came from, hour by hour, instead of trusting either.

**Three days rather than seven**, because the Engine's week is a _pattern_ keyed by weekday name and holds no dates at all. A reader shown Monday, Thursday and Saturday is shown three summaries of one routine, not three days of a story — and today and the two days ahead are the days that matter when you are deciding whether to go and find somebody. Each of the three carries the village's own date beside the Engine's weekday, so the wrapping pattern and the calendar you are actually living in cannot be read as each other, and only today's hours are ever marked as happening now.

**An hour the village has no words for does not vanish and is not faked.** It arrives as the village's default — _at home_ — and is marked as untranslated, so you can count the hours and see which of them the village has no words for. The Engine's own sentence never stands in for it: that sentence names the world the card was written for, and this package spends its time keeping that out of your village rather than letting it in through a gap.

0.4.56 is the release where **a villager's answer is read for its shape** — what they **said**, and the room going on around them. A villager's turn has always been two things at once: they tell you where you are and what they were doing, and then they say something to you. **The rule is the closing quote.** A villager describes, then speaks, and the speech is what closes the beat — so a paragraph that ends on a quotation mark is somebody talking, and one that never reaches a quotation mark is the room describing itself. Everything below is the history that led here — the 0.4.40–0.4.42 entries describe the two-way lane and the lock that 0.4.43 retires.

0.4.42 is a repair. 0.4.41 could not activate, and a package that cannot activate is not served at all — which is why Villages disappeared from Installed Agents and from Home's top bar at the same moment.

**The scene lock had to stop being a hook.** 0.4.41 kept the village closed while someone was in a scene with an `onRequest` hook, and a capability package is not handed a Fastify instance to hang one on: the Engine builds a small registrar carrying the five route methods and nothing else, gives that to the package, and registers the collected routes itself. The hook call threw on the spot, the package's server entrypoint failed with it, and the Engine recorded the package as `status: "error"` — out of Installed Agents and off Home, with nothing on screen to explain either one. The lock is now applied as each route is registered: the surface the routes in this package are written on wraps the four write methods and passes reads straight through. It sits in the same place in the request, it keeps the same three exits — taking a villager out, reading a scene back, and letting the link go — and a mutating route can no longer be added without it, because being locked is now a consequence of **how** a route was registered rather than of anyone remembering to lock it. No part of the Engine changed for it.

**And the test that should have caught this now would.** The scene suite ran against a host double that registered the plugin as a real Fastify plugin, which handed it exactly the `addHook` the real host does not have. The double was more capable than the Engine, so a package that could never activate passed every suite in the repository. The double is now built from the host's own registrar shape and asserts that it carries no `addHook`, so putting a hook back fails with the Engine's own error instead of with a package quietly vanishing from Home.

0.4.25 was the release where a conversation becomes a place you can see, and where talking to somebody splits into the three things you can actually do with a neighbour.

**The drawer has always known where this was happening and had never shown it.** A villager's own lines say it constantly — _I am just closing up_, _I have to get back to the field_ — and until now the only way to know what that looked like was to hold the town map in your head while you read. The conversation now opens on a **stage**: the picture of the place the villager is standing in, with their portrait and the place's name at the foot of it. All of it comes out of the join the village already had — the week on the character's card, the translation Villages wrote for that week, and the picture you put on the place — and it is read when the drawer opens rather than on the sixty-second poll, because the drawer is the only thing that draws a place. A villager the village cannot place keeps the same stage with no picture and the village's own name on the plate. That is not an error: a village whose week has not been translated yet has people in it who are nowhere in particular, and saying so is better than an empty rectangle.

**Where a move happens is now part of the week.** It is the one field a person writing out their week would never think to produce, so the translation is handed a **numbered list of the village's places** and each move answers with the number of the one it happens in. The number is turned into the place's identifier **at the moment the week is written**, not when it is read — a name would have to be matched back later, and a place renamed or deleted in between would then quietly re-point every older week at whatever else shared that name. Anything the numbering cannot explain — out of range, missing, fractional, a list — resolves to nothing, which is an ordinary answer that draws exactly what every other nothing draws. Someone asleep, someone walking between two places, someone doing something this village has no room for: all of them are nothing, and the player cannot tell those apart, which is the point. The identifier is also carried through **storage**, and that is the part of this that would have failed invisibly: a stored week is read back through the village's own reader before anybody sees it, so a reader that copied the week's key and its sentence and forgot the place would leave a translation that still reads as correct in every way a person can check. The reader carries it, and does not test it against the places you have now — a place renamed or deleted since the week was written is a miss, and a miss is honest.

**Talking splits into three verbs, and they are framings rather than settings.** **Chat** is shooting the breeze. **Ask** is a question, and gets an answer to what was actually asked — which is how a villager can give you the advice you were fishing for about something you think you have worked out, or how you ask one of them for something. **Fulfill** is you saying what you have already done. Each one tells the villager what kind of turn this is, so an Ask can produce the advice a Chat never would, and a Fulfill does not read as an opening bid in ordinary conversation. All three sit in one place under one composer: the only thing that changes is the box on top.

**Fulfill is the one that does not reach the villager directly.** What you claim goes to the village's judge first, and only what the judge made of it reaches the villager — which is why the framing that reaches them is set from inside the village, after the ruling, and why the route that reads a mode off a request still answers with only two of the three. Anything a caller on the same machine could name is something the package can no longer vouch for, and the whole feature rests on nobody being told what somebody is waiting on.

**And the village still will not weigh a claim against nothing.** A villager who is not waiting on anything cannot be settled with, and the village says so before it spends a word judging: a verdict of _no_ against an empty list would read as the village not believing you rather than as there being nothing to settle. So Fulfill stays on offer as a verb, and the drawer says in as many words that there is nothing to settle — the count is already on the sheet, so it costs nothing to say and saves a sentence typed into a box that could never have answered.

**Everybody has a face now, wherever the tab draws them.** The Engine's own character summaries are read in one call for the whole village — and one more, small one, when you open the picker or narrow a search — and a villager is drawn as their portrait in the stage, the tiles and the list. A character with no portrait is drawn as their initial in the same circle, which is not a placeholder for a missing picture: it is what is drawn when there is no picture, and a village of characters without portraits looks like a village rather than like a fault.

0.4.24 was the release where a villager can see their own schedule again, and where the schedule gets a place of its own to be looked at.

0.4.20 is the release where a want stops being the loudest thing in a villager's prompt. Wants were steering every conversation, and the wants were not the cause.

**A want was the only thing in the prompt asking for anything.** Everything else a villager was sent was fact — where they are, who lives here, what is on the board. One block was about motivation, and it was outnumbered by a page of description that wanted nothing at all. So the block about motivation took the whole conversation.

**And the block threw away the number that would have quietened it.** A village gives each want an intensity from 1 to 3, orders by it, and then rendered every want identically. The generator is asked to answer 1 for most things deliberately, so the ordinary case was a want the village had rated as background arriving at full volume — with no mechanism anywhere in the prompt by which it could recede. Three wants meant three things shouting at the same pitch.

**The weight reaches the villager now, in words rather than as a number.** A want that is on their mind all day says so; one that sits at the back of their mind says that; the quiet middle — the default the generator is asked to reach for — says nothing at all. The list is read heaviest first, so the order the village wrote survives and the loudest thing is the first thing read. The narrator is told the same weight in the same words, because it writes the happenings the villager then reads back, and a narrator that cannot tell a faint want from a loud one turns the faint one into news about them just as readily.

**The guardrails around the block were the problem.** They used to defend against a want reading as an errand by naming it over and over — _not a plan_, _not a task_, _not information you owe anybody_, _do not hand it over_, _rather than naming it_ — and every one of those is a fresh instruction to think about the want. The block now says what a want is, and adds the one thing it never had: permission for a reply to have nothing to do with it. The mode block's closing line said it a third time, at the very end of the prompt where recency weighs most, and that line is gone.

**`{{doing}}` finally carries a life.** The Engine's schedule status — `online`, `idle`, `dnd`, `offline` — was being read, translated into words for the debug tab, and dropped before the prompt ever saw it, even though it is the only field of a schedule that is about autonomy rather than about nouns. An hour marked as not to be interrupted is the most authoritative reason to be short with somebody that a villager can be handed, and it was being thrown away one step from the prompt. It arrives now, in the same words the translation already used. The rest of their week rides along with it, so the hour has some company instead of standing alone as one clause against a page of village facts. Both come out of a schedule that was already being read, and the texture is the translation's own moves, so this adds no read, no call and nothing to generate.

**No new macro, and that is a constraint rather than a preference.** The village's voice and knowledge are the player's own stored text, so a village that has already written its own preset would never render a macro added now, however good it was. Everything here lives inside `{{doing}}` and `{{wants}}`, which every stored preset already has.

0.4.19 is the release where the Engine's week comes into the village in the village's own terms, instead of the village wearing the Engine's.

**A schedule is written before anybody knows where it is happening.** Marinara writes a character's week from the character card alone, which is the right order — and it means the week is written in the card's world, not in the village's. A card that says somebody flies supplies produces a week that says _flying the Halcyon on a supply run_. A village with no ships and no Halcyon was reading that sentence out to its own residents, in the Engine's nouns, with the Engine's status attached.

The shape survives, the status survives, the verb is translated and the noun is replaced.

What the village does when somebody speaks is a string comparison against a table it already holds — one call a week per villager, and nothing at read time. 0.4.18 was the release where the settings panel started saying what it actually is. 0.4.17 made the villagers sound like the people on their cards; 0.4.18 was about the box that carries that, which had stopped being describable.

**One box was being asked two questions.** The thing labelled **Village prompt** held the rules about how anyone in this village talks _and_ the dozen tokens that fill in where the village is, who lives here, what is on the noticeboard and what has happened lately. Those are not two halves of one answer: one is a fact about the place, the other is a fact about today. A player editing a voice rule had to scroll past a block of macros to find it, and a player who wanted the noticeboard out of their prompts had no way to say so short of rewriting the rules around it.

**It is two boxes now.** **How everyone talks** is the village's character — how a villager here talks, what they will not do to the player, and how much they say. **The information villagers know** is what a villager here knows, written as tokens the village fills in for itself, which is what keeps them current without anybody editing anything. The macro row sits under the second box and writes into whichever one you were last typing in, because the tokens are the same in both and a second identical row of seventeen buttons would say exactly what the first row says. The panel's **Restore** button restores both.

**The fallback is by the pair, and that is where the safety of it lives.** A village that has written nothing in either box gets the shipped wording, which is what lets a better default reach the villages that never opened this panel. A village that has written **one** box gets that box and nothing else — filling the other one in behind the player's back would be the panel telling a villager something the player did not ask them to be told. A village carried over from the single-box release reads exactly as it did: what was in the old box is now in the first one, the second is empty, and the pair renders to the same characters it rendered before. No splitter, no heuristics, and no prompt in any existing village changes by a byte.

**Two areas are switched off, and left on screen.** **What this place is like** and **Places in the village** are one question with two halves — what this village is, and what is in it — and they are moving to a setup flow of their own rather than being edited here as two unrelated lists. Until that flow lands, leaving them editable would mean two screens writing the same village, and the half-edited state in between is worse than not being able to touch them at all. They stay on screen rather than coming out because what is in them is still real and still working: the setting still reaches every villager through the town description, and the places still reach them through the town map. Both are still read from the record and still written back with the rest of the panel, so nothing already written is lost or has to be typed again.

No route changes shape and `engine.min` does not move: one more field on a record the village already keeps, one more field on a snapshot it already sends, and a default string split in two. The one cost is a restart, because the second field is stored.

0.4.17 is the release where the villagers start sounding like the people on their character cards. 0.4.16 gave everything you do somewhere to show up, and gave the village a shared story; this one is about the people doing it, and it turned out they had never been told how to talk.

**The problem was the preset.** A village runs **one** prompt across the whole cast, and the one it shipped was a list of prohibitions: don't write the player's words, don't prefix your own name, no asterisks, don't invent facts, keep it short. Every one of those is correct, and every one of them is about what a villager may not do. Not one sentence said whose voice to write in. Told what to avoid and never told who they are, a dozen villagers answer out of one mouth — polite, even-tempered and interchangeable, which is what stiff and robotic actually looks like from the inside.

**So the default now leads with voice.** It runs on the same ideology Marinara's own preset runs on, in the same register, inside the document you already own and can still edit: this person is real and going about their own day, not a narrator and not the village speaking; **your voice comes from your own description and your own personality**, and that is where the vocabulary, the rhythm and the amount you bother to say come from. Then the two rules that do the real work of keeping a cast apart — nobody here sounds like anybody else, and how you talk follows how you feel, right down to the interruptions, the half-finished sentences and the going quiet. The prohibition list is not gone. It sits behind them, because the same sentence reads as containment where it stands alone and as character once the voice rules have gone first.

**Two words had to go.** "Ordinary speech" appeared in the preset **and** in the greeting direction, and to a model ordinary means unremarkable — a rule meant to keep replies short was flattening the register to nothing as well. Both now ask for a line or two in the villager's own voice, and leave what that sounds like to the character.

**Two card fields were missing.** Backstory and appearance are where an Engine card keeps both, and the Engine hands them to the model by default — so the package was quietly giving a card's author less than the Engine does, and a character whose voice lives in either field read as generic here for exactly that reason. Both are read now, and each appears in the identity sheet only when it has something in it.

**Example dialogue now says what it is for.** It was already being handed over, as a bare block of the character's own past lines — which a model reads as a template, so a villager answers by reaching for lines the card already contains. The block now says those lines show the register to write in and are not lines to reuse, which is the parroting failure the Engine's own preset names outright.

Nothing here needs a newer Engine: a rewritten default string in a document you can still edit, two more card fields read from a payload the package already receives, and the body of a heading. The card's own `system_prompt` still goes in first and is still never rewritten, and `first_mes` is still deliberately unread.

0.4.16 is the release where what you do is part of the village straight away, and where the village's storyteller can finally read the village's own shared story. 0.4.15 gave an afternoon's conversation somewhere to go and gave a want something to come of it, but both of them went somewhere the player could not see — on a clock the player does not control.

**The problem was a clock.** Ending a conversation wrote a memory, and a memory is read by the villager it is about and by nobody else. So you could sit with someone for an hour, say the thing, watch the answer land, and then find the village exactly as you left it: the panel that draws what has just happened, the board the villagers talk on, and every prompt that carries the news all went on saying the same weather. The only writer of any of it was the part-of-day write-up, and that runs when the part of day turns over — up to four times a day, decided by the clock rather than by you. Answering a want did not even manage that much: the favour was filed on the record and the run of days carried on as if the roof were still open.

**The lever was already there.** `happenings` is the window the player watches, it reaches every villager prompt through `{{happenings}}`, and the story reads it back as its own recent news — so one line written there is a thing you can see, a thing the villagers know, and a thing the village's story will not contradict, all at once. Nothing wrote it except the write-up.

**Nothing new was invented to write it.** Ending a conversation already puts the transcript in front of a model and is already the one moment the package knows the conversation is over, so the village's news now rides on that same reply: one call, two lists, one single write to the record, because two writes are two chances to keep one and lose the other. The reply may now carry a line about what the rest of the village saw or heard of the conversation, and the prompt is explicit that **an empty list is the usual answer and the right one** — most conversations are nobody's business. A settled want has no such call to ride on, because the judge is asked a yes or a no rather than asked to write, so a want that **was** settled pays for one small call of its own, out of band, after the answer has already gone. A want that was not settled asks nothing and costs nothing, because a refusal is not news.

**That extra call is handed the judge's line and never your claim**, and the difference is the whole safety of the route. Your claim is the one sentence in the path that nothing has checked yet — it is what somebody said, in a village that has no way to look. The judge has already read the record and decided it was true, and what the judge wrote is the part that was decided. Feeding the claim to a writer would be the one way your own words could be written into the village's news as fact.

**The story can read the shared story now.** The narrator was handed the happenings window and nothing else, so a conversation that had been remembered and had since fallen off the end of forty lines was a thing the village knew and its own storyteller did not — and the deeper the history got, the more of it there was. A `## What the village remembers` section now carries the memory entries filed against the village as a whole, oldest first and capped. Exactly two rules keep it honest: memories private to one villager are not in it, because that would hand a confidence to the whole square, and anything the window above already carries is deduped out, because saying a thing twice spends the prompt's room on saying it again.

**Both writers describe a happening in the same words.** The rule that says what a happening _is_ — a change somebody could see from outside, not a mood and not a resume of the village's own story — was written once for the write-up, and a second writer working from a paraphrase of it is a second writer that drifts. The rules are now one list that both writers are handed, while the count, the framing and the shape of the reply stay with the writer they belong to.

**DEBUG gets a Write it up now.** A feature that mostly shows its work when the part of day turns over is a feature nobody can test, so this bypasses the two automatic switches: the bookmark that says this part of day has already been written, and the part-of-day setting that says when the village writes at all. It bypasses nothing else. The window is still deduped against, so forcing a part of day with nothing new in it adds nothing rather than inventing something to justify the call; and the bookmark still moves, because a forced write **is** a write-up of that part of day, and leaving the key behind would make the next ordinary one cover the same afternoon twice. The menu says so alongside the button, and the button reports what it did.

No route is added. `POST /api/villages/tick` reads an optional `force`, strictly as the boolean `true` and nothing else, and an empty body is still an ordinary call. No permission is added, and `engine.min` does not move: one more field in a prompt the village already builds, one more section in another, one more meaning for a record the village already keeps, and a flag on a route it already had. The honest cost is that a settled want now spends four calls in total — the judge, the reply, the quiet follow-up that asks what they want next, and this one.

0.4.15 is the release where a want can be answered, and where a character card stops writing the first thing you see. 0.4.14 gave every villager something they wanted and kept it carefully out of the player's reach, which left the want with nowhere to go: it coloured a day, and then the day ended. This is the other end of it — and one piece of the old behaviour had to go first.

**The card's opening line is no longer part of the village.** `first_mes` was read as the villager's greeting and written into the transcript when they moved in, which meant the first thing anybody saw in a Villages conversation was a line written for the Engine's own chat surfaces: with `{{user}}` and `{{char}}` macros left unexpanded, staging a scene the village never staged, and tuned by the author's own tone settings, which the village does not use. A moment later the real greeting arrived, so an opening turn came twice and in two registers. The field is now off the type rather than merely unread — the reader does not touch it and nothing downstream can — so a card's opening line cannot reach a transcript, a prompt or a tile by accident. The only greeting left in the package is the one a villager writes for themselves, standing in the room they are actually in, answering whoever is actually there. If the model cannot manage it, the village says something **character-neutral** instead, because a silence at the door is worse than a plain hello. That hello is written once, under an emptiness re-check performed by the write itself rather than by the caller, so two visits seconds apart produce one greeting and a room that already has something in it costs nothing at all.

**Talking to a villager now has two shapes.** Chat is the ordinary thing it always was. **Ask something** says so in the prompt — go straight at what was actually asked, in a sentence or two, do not change the subject, do not deflect to something you would rather talk about, do not tack on news of your own — because a villager handed a question and a life will answer with the life. Declining is still allowed and still has to be honest about which it is: "I am not going to tell you that" is a different thing from "I do not know", and neither is answering a different question. The mode is the shape of the question and not a fact about anybody, so it is sent with the line and stored nowhere.

**A want is settled by somebody who was not there.** The player writes one line about something they did, and a **separate call** reads the record and decides whether anything actually happened. That separation is the whole design. The villager is a _party_ to the claim — they have just been told, by someone being kind, that something was done for them — so asking them whether it was done is asking the one participant who cannot be objective, and a villager merely _asked_ to be strict is lenient the first time a model returns something unexpected. The judge is cold, is handed the transcript, the happenings and the memories themselves rather than a summary of them, and must name the **id** of the want it says was settled. A yes that does not name a want this villager actually has is coerced to a no, a missing or unreadable answer is a no, and partial credit does not exist: saying a thing is not doing it, and a promise, a plan, an intention or a feeling is not a deed. The villager is then told the verdict as a fact, and told **nothing** of the reason — the reason is the judge's, and the villager already has their own opinion of you. The player is owed it, so it is drawn under the reply as a small footnote: green when they were believed, red when they were not.

**What a settled want leaves behind is a favour, and the first thing in the record with a weight.** A want's intensity was already how much of the writing room it got; it is now also how much the favour it became is worth remembering, and the entry is filed with a favour kind at that weight. The chronicle is trimmed by that weight rather than from the tail, so a long afternoon of small talk can no longer evict the one entry that is not interchangeable with the others — the record of what the player did for somebody is the last thing the village forgets about them. A settled want is replaced rather than lost: after the answer has already gone, the village is asked what that person wants next, quietly and out of band.

In the drawer, the verb appears only when there is something it could settle, and the wants themselves are still never shown — not the texts, not the tells, not even a count. Working out what somebody is short of by paying attention is the game, and a drawer that listed it would turn a private want into a quest log. In the story tab a favour is marked as one, since it is the only entry in that list the player caused.

Two routes are added on the package's own surface, `POST /api/villages/villagers/:characterId/greet` and `POST /api/villages/villagers/:characterId/want`, and the conversation route takes an optional `mode`. No permission is added, and `engine.min` does not move: two more fields in the village's own stored record, one more shape in a prompt it already builds, and no Engine surface touched.

0.4.14 is the release where the people in the village want things, and the day is written by somebody who knows it. 0.4.13 let a conversation be ended and remembered, and 0.4.12 gave the village a memory to write to, but both are about what has already happened. Nothing yet knew what anybody was _after_, and that is the difference between a village and a weather report: an event happened **at** the place rather than **because** somebody in it was up to something.

So every villager now has an **agenda**: one to three wants, each carried with the small ordinary thing that gives it away, plus the day they live on every other day. It is worked out once — from the card, and from the Engine's own weekly routine for that character when there is one — and kept on the villager's own record. The Engine stays the authority on a character's time; the village writes around the life you have already given them rather than inventing a second one beside it. A villager who moves in is asked about straight away, and anyone who has not been asked about yet is asked on the next part of the day the village is written for. That second part matters more than it sounds: it means a village that already existed is written about as people from its very first tick, instead of over the days it would take to work through a roster.

The whole safety of the feature is in how a want is described, and it is said the same way in both prompts. To the narrator a want is motivation — the reason behind a happening that was worth writing down on its own. It is never a happening by itself, never announced, never asked after, never advanced and never resolved. To the villager it is theirs, and private: `{{wants}}` renders it with a closing line that says outright that these are not a plan and not a task, and that exists because the alternative — a bare list of things somebody wants sitting in a chat prompt — is a character who opens the conversation with their shopping list. Each want carries an id it can be addressed by later, because a want is the kind of thing somebody may one day be able to be given something about.

You can look at it, and that is all: **Menu → DEBUG: Villager Wishes** — the tab this release shipped as **Villager Wants**, renamed in 0.4.71 along with the macro, which is `{{wishes}}` — draws every villager's agenda with the day they live on and whether it came from the Engine's schedule or from the village's own invention, and **Write it again** clears one so the next part of the day rewrites it. There is no surface in the village itself, nothing a villager decides, says or is prompted with is read from here, and the read is on its own route rather than folded into the snapshot — which is re-sent on every keystroke of every chat, and this is one model call's worth of text per villager. Two routes are added for it, `GET /api/villages/agendas` and `DELETE /api/villages/agendas/:characterId`, and no permission is added. `engine.min` does not move: the agenda is one more field in the village's own stored record, one more macro in the preset, one more section in a prompt it already builds, and the routine comes from the read-only schedule access the village already had.

0.4.13 is the release where a conversation with a villager can be **ended** rather than only forgotten, and it exists because of the one thing that happens in a village which nothing else can see. 0.4.12 gave the village a memory, but the record was written by the tick — by the village about the village — so an afternoon spent talking to somebody left exactly no trace of itself: the lines lived in a transcript that gets deleted, and a villager could be handed the whole of the village's history and still not know what you said to them yesterday.

So the conversation drawer offers two ways out of it, and the difference between them is the whole point. **Forget** throws the conversation away and the village never learns it happened, exactly as before. **End conversation** asks the villager what they took from it, files the answer on the same chronicle the tick writes to, and only then deletes the lines. That order is not a preference. A clear that ran first would leave the model nothing to read; a clear that ran after a failed call would lose the conversation _and_ remember none of it, so the village would have paid for an afternoon and kept nothing but the gap where it used to be. Nothing is cleared until a real answer has been stored, and a failure leaves the conversation exactly where it was for you to try again — which is why the operation is a `POST` on its own sub-path rather than a reuse of the delete. Everything a conversation leaves behind is about the villager who was spoken to, and it is private or shared on the same terms the tick's memories are, so a line that passed between the two of you is never handed to a third person. A conversation you never took part in — a greeting, and nothing after it — is closed without a model call, because asking a model to remember a hello is paying for nothing.

Beside it is **your own copy of what was actually said**, which is the one record in this package that nothing in the village ever reads. It is written a line at a time as the conversation happens, so a tab closed in the middle of one is not a conversation lost, and ending a conversation and forgetting one both draw the line between one conversation and the next inside it. It is readable back from **Menu → DEBUG: Chat Logs**, which says how many conversations and how many lines each villager has and opens into them grouped by the day they started — the day and the part of day derived from the same clock the story uses. One conversation can be discarded from there; the rest is read-only. It is a DEBUG tab for the same reason the story is: seeing the record is how it gets reviewed. Because nothing builds a prompt from it, a fault in it can never change how the village behaves, which is what makes it safe to keep however odd what it holds turns out to be. Three routes are added for it — `GET /api/villages/chatlogs`, `GET /api/villages/chatlogs/:characterId` and `DELETE /api/villages/chatlogs/:characterId` — and, like the story's, no permission is added.

Two smaller things come with it. A villager whose card is deleted keeps their record and keeps their place in the chat-log list, because losing your own copy of a conversation because a card was removed is the tab forgetting on your behalf; a villager who is removed from the village takes it with them. And **Start over** clears the chat logs along with everything else — read as a list rather than walked off the roster, because a villager moved out of the village keeps their record until somebody throws it away, and a reset that left one of those behind would leave a conversation with nobody on the debug tab. `engine.min` does not move: the memory lands on the record the village already keeps, and your copy is one more package document.

0.4.12 is the release where the village starts to remember, and it exists because of a question the last few releases kept circling: if the news is a window that holds forty lines and drops the oldest one forever, what does a village actually _know_? A village a month old had a month of events and nothing it could still refer to, and a conversation you had with a villager was invisible to the village entirely.

So there is a second record with a second lifetime. `happenings` is untouched — it is "what has been happening lately", and a window is the right shape for that. Beside it the tick may now write a `chronicle`: the few things worth still knowing about in a month, which the news will have forgotten long before. A memory is filed against the same day and part of day a happening is, so the two can never disagree about when something was; it may be shared, or private to the people it names; and both records land in the same single write, because the store replaces the whole row and a second write is a second chance to keep one and lose the other.

A villager is then handed what they remember, through a new `{{memory}}` macro: the shared story, plus whatever was private to them, and never anybody else's private lines. The selection is a join on the card id rather than on a name, so renaming somebody does not hand their memories to somebody else. The two budgets are separate and deliberately lopsided — a shared story is the same for everybody, while a private one is only ever about one person, and a villager who cannot forget your one visit is a character trait where a villager reciting a dozen of them is a log file.

Both blocks are dated now, and both say how long ago in words. That fixes a bug rather than adding a feature: a line of news used to render as bare text with no date on it at all. But storing a date is not enough on its own, and that is the lesson this release is built around — a model handed "Day 3" and "Day 5" does not reliably subtract them, and a villager who says a Tuesday conversation happened this morning is wrong in the direction nobody notices. So the subtraction happens in code and the model is handed prose: `12 September — three days ago`. A day that cannot be placed before or after the clock is dated with no age rather than guessed at, and one that is somehow ahead of the clock reads as "recently" rather than as a future, because a restored backup or a corrected system date should not make a village remember tomorrow.

The whole of it is readable. **Menu → DEBUG: Village Story** draws the record, grouped by day, with each private memory saying who it is private to — read-only, apart from forgetting one entry by id, which is there to take back a line that was never true. It is a DEBUG tab on purpose: what the village believes is worth being able to look at, and it is not a thing the player should be editing by hand. Two routes are added to the package's own surface for it — `GET /api/villages/story` and `DELETE /api/villages/story/:id` — and no permission is added. `engine.min` does not move either: the chronicle is two more fields in the village's own stored record and one more section in a prompt it already builds.

0.4.11 is the release where the homepage stops being a picture with things written on it and becomes a page with a picture on it. It is a small release by design — no route, no record, no prompt and no Engine version moves — and it exists because of what the last few releases kept running into: the Engine's own side panels.

The news used to be a window laid over the map. It was positioned a fixed distance in from the tab's top-left corner, and that looked right for exactly as long as the tab was wide. The map is a picture of a fixed shape drawn as large as the tab allows, so on a wide tab it is limited by the tab's **height** and sits narrower than the tab, leaving a gutter down each side — and the window, being in the left gutter, read as a panel beside the map. Open the Engine's sidebar, or its settings panel, and the tab narrows until the map is limited by the tab's **width** instead: it fills the tab edge to edge, the gutter is gone, and the window that was sitting in it is now sitting on the picture. Nothing was wrong with the window. What was wrong was that it and the map were not laid out relative to each other at all.

So the homepage is a row of two columns now: **The village** down the left, the map in what is left of the row. The map is fitted against the column it is given, so whatever width the tab ends up with, the two are a narrower map beside the news rather than a map underneath it. The corner readout, the **Menu** button and the notices moved onto the picture with it, into the map's own frame and offset from the picture's own corner. The column is the box the map is _fitted to_, not the box the map _is_: the picture is centred inside it, so a corner hung on the column is on the picture on whichever axis is limiting it and out in the gutter on the other one — which is where the news is. The frame is the one box whose corner is always the picture's corner, so the three of them hang there and nowhere else. A villager's conversation is deliberately still the one thing that slides in over the whole tab — it is about a house on the map, not about the map's layout, and it is opened and dismissed by the player rather than arriving on its own.

Three old assumptions went with the old shape. The news no longer starts below where the readout was assumed to end, because it is a column rather than a window pinned to the tab's corner. The news no longer carries a ceiling of its own — it is capped by the row, so a long list scrolls inside the tab rather than growing past it — and it is capped in **width** too, so the map always keeps around two thirds of the row. And the homepage no longer has a **minimum height**: a floor taller than the visible tab is a floor the map is fitted against and then clipped by, which is how a short tab used to give you the middle of a big map with its top, its bottom and the pins on them cut off. A short tab now gives a small map.

The map also wears a frame. Two layers are painted around it — wood, and the mat inside the wood — as CSS gradients, plank bands and grain and no new file. The frame is drawn **outwards** from the map's own box rather than into it, and that is the whole reason it can be added without moving a pin: a frame drawn inside the map's box would have to come out of the picture, and a picture cropped to make room for its own frame is a map whose corner houses have gone. The buffer the frame lives in is the map column's own padding, and the map is now measured to that padding rather than to the column's edge, so the frame cannot be clipped by the box that has to clip a pin. The frame is on the homepage only; the founding wizard and the **Town map** editor keep the plain border they had.

0.4.0 is the release where the village carries on without you watching. 0.3.6 was built on a claim that turned out to be false — that a capability package gets no timer, so the tab had to be the only clock — and the claim is worth correcting out loud, because it is the reason a village left alone overnight had nothing to say when you opened it again. There is no missing Engine feature here. The module-level `setTimeout` that Noodle and Slurp already publish on is available to any package, and Villages simply never started one. So the tab was never the mechanism; it was only ever the thing that happened to be open.

The package now wakes itself up. `village-refresh-scheduler.ts` arms a timer for the next part of the village day plus a small settle, and arms it again after every wake, so the village is written up within a minute of 05:00, 12:00, 17:00 and midnight whether or not the tab exists. The delay is capped at an hour, because the longest gap between two parts of a day is five hours and waking every fifteen minutes to write four times a day is ninety-six wake-ups to produce four entries — a wake that arrives early finds the part of day unchanged and costs one read. `runVillageTick` itself is unchanged: the same no-argument call the tab has always made, which is why this needs nothing from the Engine and `engine.min` does not move. The timer belongs to the cleanup `activate` already returns, so deactivating the package stops it, and it is unreferenced so a pending wake cannot hold the Engine's process open.

Two preferences come with it, in **Menu → Village settings**. **Update on its own while you are away** is the master switch. **When it may update** is one switch per part of the day — morning, day, afternoon, evening — because "update on its own, but never in the evening" and "update in the evening only" are both reasonable things to want and neither is sayable with a single switch. They are stored as a list of parts of the day rather than four flags, and an empty list is a real answer rather than an unset one: a village with automatic updates on and every part of the day off writes nothing while you are away, which is a different thing from a village whose preferences were written before this release and therefore gets all four.

Both rules are enforced inside `runVillageTick` rather than at the switch or in the scheduler, because the tab and the timer are two callers and a rule kept by one caller is a rule the next caller forgets. A part of the day switched off costs no model call whoever asked for it, and the part of day is left **unmarked** rather than marked-but-skipped — so switching it back on still writes that part of the day instead of losing it, which is what makes the switches reversible rather than a way to quietly drop an afternoon. The master switch deliberately does not stop the tab: turning automatic updates off is asking to be the one who decides when the village moves, not asking to open it and find it frozen, so the tab still catches up the moment you look. And the re-arm is decided by the clock alone — a wake that wrote nothing is retried on the next wake — which is what makes a provider that was down for an afternoon cost one batch rather than an afternoon of them.

0.3.7 lets you say who you are by pointing at a **Persona**. The founding wizard's first step asked about the village and nothing about you, so the name the villagers call you was only reachable afterwards, in **Menu → Village settings** — which meant a village could be founded and then lived in by "the player" until you went and found the field. That step asks the second question now, and it takes either answer: pick a Persona out of the Engine's own library, or keep writing the name and the description by hand. The wizard and the settings panel ask it with the same control and the same words.

A Persona is a **link**, not a copy. The village stores the id and reads the Persona every time it needs to know who you are, so editing that Persona in the Engine's own editor changes what the villagers believe without the village being touched again — and a person you are still writing is a person the village has not made up its mind about. It is read whole: display name, description, appearance, personality and backstory, because a villager who has been told your name and one line about you is a villager who invents the rest.

Choosing a Persona **hides** the two typed fields rather than clearing them. What you wrote stays on the village record and comes straight back the moment you pick **Not set** again, so trying a Persona is not a decision you have to be careful about, and the panel says plainly which of the two answers is in force. A broken link is kept and said out loud: a Persona deleted out of the library leaves the village linked to an id that no longer resolves, the panel tells you so, and the villagers fall back to your own words rather than the village quietly forgetting who you are. Reading Personas asks for no new permission and needs no Engine change — the list comes off the same resource host the character library already does.

0.3.6 is the release where the village starts keeping its own news, and stops writing anything down before you get there. Two things used to be true that should not have been: a new village opened with three notices already pinned to its board, as though somebody had been living there, and **Suggest places** wrote a few of those notices itself, which is a question about the geography answering a question about the people. Both are gone. A village you have just founded now opens on an empty board and an empty record, because nothing has happened here yet and nobody has had the chance to want anything.

In their place the village writes its own **happenings** as its clock turns. `POST /tick` works out which part of which day it is and, when that is a part of day it has not written for, asks the model for a small batch of things that have already happened — a delivery, a broken latch, a spill, a shouted argument across the square — and a note or two for the board in a resident's own voice, signed with their name. What comes back is filed against the part of the day it belongs to rather than a wall-clock stamp, because a timestamp is the one fact in the record that could disagree with the clock the tab draws: there is exactly one reading of what time it is, and the village's own clock is it. Nobody is killed, maimed or seriously harmed, and nothing decides what anyone _feels_ about what happened — the village says what happened and leaves the meaning to you.

The happenings are drawn in a small window down the left of the map, **The village**, newest first. It is deliberately not the noticeboard: the board is what the villagers say to each other, in their own handwriting, and most of it is a request; the window is what happened to the place, in the narrator's voice, and none of it is aimed at anybody. A village with a full board and a quiet window is a village getting on with things. (0.4.11 corrects the word: it is a column of the row rather than a window over the map, because a window over the map only reads as a panel while the tab is wide enough for the map to leave a gutter for it.)

The tab is what drives the tick, because a capability package gets no timer — one call when it opens, and one whenever the part of day it is holding turns out to have moved on. (0.4.0 corrects the reason given here: packages do have a timer, Villages just had not started one, so the tab is no longer the only thing that drives the tick and a village now keeps moving with nothing open.) Both are gated on a single stored string, `lastHappeningKey`, naming the part of day already written for. So reloading the tab, or opening a second one, costs a read and nothing else, and two tabs cannot write the same afternoon twice. It also means the honest thing happens to a village you have been away from: a week away is one batch about the week — the village is as alive as the days it actually lived through — rather than twelve model calls catching up one part of a day at a time, or a week that never happened. A tick that fails writes nothing and does not advance the key, so the next read tries again rather than losing the part of the day; the failure is logged and the tab is told nothing, because a window a part of a day behind is a small thing and a language-model error is not something you can act on.

Notices now carry who wrote them: `string[]` became `{ author, text }[]`, and the board renders the name first, the way a note on a real board is read. Your own pins are left unsigned — everyone here already knows who you are, and an unsigned note is an ordinary thing to find — and the villagers' prompt is told in as many words what an unsigned note means, so nobody has to guess. A board written before this release is read rather than discarded: an old plain-string note is an unsigned one, because dropping somebody's writing to make a schema tidy is not a trade worth making. Notices reach a villager through a reworked `{{noticeboard}}` (a heading, one signed line per note, or nothing at all) and the village's news reaches them through a new `{{happenings}}` macro, rendered oldest first — a villager reads their week forwards, even though the record and the window hold it newest first.

**Look again** is gone. It read the village afresh and stayed put, which was worth a button when reading was the only way anything arrived; the village comes to the tab now, so the button was asking the player to do by hand what the tab does on its own.

0.3.5 takes the escape hatch out of the founding wizard. Its bar carried a **Later** beside the village's name, and Later was never a way out of anything: it put the player on a homepage for a village that did not exist yet, and the next time the tab was opened the village still did not exist and the wizard was asked for all of it again, because nothing is written until the last step. So the bar is a title now and the end of the wizard is the only door out of it. A village that already exists is not shut in by that — running setup again still has **Save this village**, which leaves by the same door but keeps the answers, and **Show me the village** beside it, which leaves without keeping them.

0.3.4 keeps the whole map on the screen. A frame drawn at the map's own shape but laid out as wide as the homepage — the width of the entire tab — is a frame taller than the tab, and the tab clips it. What a clip takes off a map this shape is its top and bottom, and the corners of a map are where a player puts their first four houses, so the four houses on the four corners were the four houses that could not be opened. The homepage now measures the room it is drawn in and takes the largest frame of the map's own shape that fits it — the smaller of _as wide as the room_ and _as wide as the room is tall_ — and gives the frame both of its sides, so the ratio cannot be broken again. Every other stage keeps taking its width from the column it sits in, where the room is not a ceiling. The pins are drawn as the thumbtacks they are named after: a small red pushpin, drawn inline rather than taken from a font or an emoji so it is the same tack on every machine the Engine runs on, and grey rather than red for a house nobody has moved into yet — the colour the dot it replaced used to carry. The wizard's step strip stopped being a control. It says where the wizard has got to and nothing on it answers the cursor, because a chip that leans forward when the pointer crosses it and then does nothing when it is clicked is promising something it cannot keep; **Back** and **Next** are what walk the wizard. And founding a village no longer offers to show you one: **Show me the village** is only drawn once the village exists, since a first-time wizard has nothing behind it to go and look at. **Later** in the wizard's bar is left alone by this release, so a first-time wizard can still be walked away from here; 0.3.5 takes that away.

0.3.3 decides how a map is drawn instead of hoping it agrees with the frame. A map is now a fixed shape — `TOWN_MAP_EXPECTED_WIDTH` and `TOWN_MAP_EXPECTED_HEIGHT` in `services/villages/prompt-preset.ts`, `1080×566`, the shape of the art the package ships — and the frame is laid out at that shape whatever shape the tab happens to be, so a map is never quietly letterboxed into a band of tinted background, and the pins are placed against the picture rather than against the frame around it. How a picture that is _not_ that shape is made to fit is a stored decision rather than an accident: `settings.townMapView` carries the **fit** (`cover`, `stretch` or `contain` — the CSS `object-fit` values themselves, so the choice the server stores is the choice the browser is given), where the picture is aimed (`focusX` and `focusY`, as percentages) and how far it is magnified (`zoom`, stepping from `settings.townMapZoomMin` to `settings.townMapZoomMax` by `settings.townMapZoomStep`). The village owns those numbers and the tab restates none of them. Picking a picture is a conversation now rather than a write: the file is decoded, measured and drawn in the real frame, the tab says what is actually true of it — a picture smaller than a map will look soft, and stretched as well if its shape does not match — and then you choose how it sits, drag it to the part you want and save. Taking a map down takes its framing with it, because a crop of a picture that is not there is not a thing that can be drawn. The founding wizard's first step now shows the map small and inert, as the thing being named rather than somewhere to click, and the starter homes are pinned on the next step at the size a map is really drawn at.

0.3.2 gave the map the whole tab. The four panels that used to sit in a column beside it — **Villagers**, **Noticeboard**, **Homes** and **Town map** — moved into the **Menu**, which is now the only thing drawn over the picture besides a small date and time in the corner and the **Menu** button next to it. Nothing else is layered on the map, so a house is placed by clicking the map itself, and the **Menu** button hands the tab over for one click and brings it straight back with the new row on the list. The menu is grouped: **Village Management** holds the four panels, **Village Settings** and **Look again**, and **General Settings** holds the setup controls and the reset. **Look again**, which used to sit in a bar under the map with the `N living here` count, is a menu entry now, so reading the village afresh leaves the panel you are looking at open instead of throwing you back to the map. A villager's conversation is the exception to all of this: it slides in from the right over the map, about a third of the width, and the close button slides it back out of frame. Picking a villager in the menu hands the tab to the map with their conversation arriving with it, because looking at the map and talking about it are the same screen. The date and time in the corner is the **device's** real clock, not the village's — the village's own clock is the language model's idea of the time of day and only moves when something is sent — and it is rendered in whatever the machine's locale says, so it reads `2:30 PM` or `14:30` without a setting for it. The weather chip and the resident count are gone; both are expected to come back in a different form.

0.3.1 fixed the map failing to appear, and kept the pins on the picture once it did. A file that is copied into the package and hash-pinned in `manifest.files` is still **not servable**: the Engine's asset route only hands back a path named in `contributions.homeBrowserTab.iconPaths` or `contributions.assets.paths`, and 0.3.0 named the map in neither, so `/api/capability-packages/villages/assets/villages-townmap.png` answered `404` and the homepage and the setup wizard both drew an empty black frame. The map is now declared in `contributions.assets`, which is a Capability API 1.10 feature, so the package also ships a `schemaVersion` 2 manifest carrying a `capabilityApi` and the build provenance pinned in `packages/villages/engine-boundary.json`. The picture was also fitted inside the frame rather than stretched to it, and the box it is actually drawn in is measured from the decoded image and the frame, so a pin sits on the building the player clicked instead of on the margin around the map — and a picture that will not load now says so rather than leaving a blank panel. The map also stops at the number of houses the wizard asked for: the server accepts a founding save only when it carries exactly the four houses it asked for, so a village that is still being founded holds the map to that count rather than letting a player place pins the save would have rejected, and only a village that already exists is held to the settings ceiling. Finally, the tab is laid out as **two columns** instead of a picture with controls layered on it: the map keeps a framed panel of its own and the clock, the panels and the wizard's questions sit in a column beside it, so no control is ever drawn over the map. The columns are measured in `rem` and allowed to wrap, which is what makes the layout answer to the Engine's own side panels — as they open the tab gets narrower, and past a point the map drops underneath the controls rather than being squeezed to a sliver beside them. Every home is also a **building** rather than a name the player types: the village owns a small catalogue of them, each with a class it belongs to, and a home the player places is a **small home** in the **housing** class. The tab asks no question the catalogue has already answered, and a villager holds one home and no more — the wizard strikes a villager who already has a house off every other row, so the mistake cannot be picked rather than being refused after the fact.

0.3.0 makes the town map the village itself. A bundled map ships as a package asset, so a village has art before you do anything, and the tab draws it full-bleed as the whole homepage: the clock, the weather and every control float over the picture, and **Villagers**, **Noticeboard**, **Homes** and **Town map** open as overlay panels that fold away again. A new village also opens a **setup wizard** — name the village, say what it is like and what the villagers call you, place four homes on the map (one of them yours), then choose who moves in. Pins are buttons: a villager's pin opens their conversation, and yours is marked **You**. **Menu → General settings** offers both **Run setup again** (keeps every villager and conversation) and a confirmed **Reset the village and start over**. Homes are stored on the village record and reach the villager prompt through the new `{{homes}}` macro.

0.2.4 gave the homepage a **Town map** panel: a picture the player supplied from **Menu → Village Settings → Debug — town map image**, stored on the village record and drawn above the villagers. The image is kept exactly as it was picked — an over-large one is refused with both sizes in the message rather than silently re-encoded — and it travels on its own `GET /api/villages/town-map` route, because a snapshot is rebuilt on every chat send and a picture in it would be re-sent whole every turn. The snapshot carries only a stamp, which is what tells the tab to refetch. In 0.3.0 that control is a real **Town map** panel and the uploaded picture is the _override_: **Use the village's own map** clears it and falls back to the bundled art. ### The town map

The town map is a logical coordinate surface first. Venue positions are stored as fractions from 0 to 1, so the same pins remain aligned as the frame scales from desktop to mobile. A generated or uploaded picture is optional decoration beneath that surface. With no picture, the frame draws a quiet logical-map background and remains fully interactive.

The founding wizard generates at 1216×832, the same 19:13 shape the frame publishes through `settings.townMapExpectedWidth` and `settings.townMapExpectedHeight`. Uploads should be 1216×832 or larger at that shape. The browser checks the file size and decoded dimensions before holding it, the server validates the data URL and storage ceiling again, and the final setup request writes the village and map together. A generated map is invalidated when its setting or structural prompt changes, so the wizard never quietly saves artwork produced from stale instructions.

Home positions are stored as **0..1 fractions** of the map, never pixels, so the pins land on the same buildings whatever the map's resolution and whatever size the window is. The fractions are read against the box the picture is actually drawn in, which is measured rather than assumed: the frame is a fixed shape, the picture is made to fit it by the framing the village stores, and the drawn box falls out of the decoded image's size, the frame's size and that framing. So a fraction is a position **on the picture** — a pin on the letterbox beside a picture that does not fill the frame is not drawn on the map, and a click there is not a position the player chose, which is why the frame is tinted precisely so that margin does not read as part of the map. Anything outside that range is refused rather than clamped to the edge. `MapStage` watches the frame — and, on the homepage, the room the frame is drawn in — so the framing is recomputed when the window or the pane is resized instead of being frozen at the size the picture happened to load at.

A pin is drawn as a thumbtack, which is what the thing on a map actually is: something pushed through the paper to say a building is here. The tack is an inline SVG rather than a font glyph or an emoji, so it is the same tack on every machine the Engine runs on, and it sits in the same chip as the name it labels, which is the part that takes the click. Red is the tack's own colour rather than a theme's, and a pin for a house nobody has moved into yet is drawn grey: the tack says _a house is here_, and what it is coloured says whether anybody is.

The frame's shape is the map's own rather than the tab's, and it is the village's fact rather than the tab's: `settings.townMapExpectedWidth` and `settings.townMapExpectedHeight` are sent on the snapshot and the frame is laid out at that ratio, so the same picture is drawn at the same shape in the homepage, beside the wizard's questions and in the Town map panel. A picture that is not that shape is made to fit by `settings.townMapView`, and the three fits are the three honest answers rather than three ways of saying the same thing:

| Fit       | What it does                                                                                                                            |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `cover`   | Keeps the picture's own shape, fills the frame, and crops whatever hangs outside it. Draggable, and the only fit that can be magnified. |
| `stretch` | Squeezes the whole picture into the frame. Nothing is cropped, and a picture whose shape does not match is drawn stretched.             |
| `contain` | Keeps the whole picture and leaves the frame's own background around it.                                                                |

The frame's shape being the map's own means how big the frame can be is a question with two answers rather than one. The homepage is the whole tab, so there the room is also a ceiling: a frame laid out as wide as the room is a frame taller than the room, the tab clips what it cannot hold, and the part a clip takes off a map this shape is its top and bottom — which is where a village's corner houses are, and a corner house nobody can see is a house nobody can open. So the homepage measures the room it is drawn in and takes the largest frame of the map's shape that fits it, the smaller of _as wide as the room_ and _as wide as the room is tall_, and gives the frame both of its sides so the ratio cannot be broken again. Every other stage sits in a column sized by the prose beside it and takes its width from that column, which is the one place where measuring the room from the map inside it would be measuring a box against its own contents.

`focusX` and `focusY` are the point of the picture held in the same place in the frame, and they are used raw as `object-position` percentages when the zoom is at its minimum — the Engine's own portrait focus works the same way, so the numbers mean what they already mean elsewhere. The CSS is given the same percentage twice on purpose: `object-position: X%` holds the picture's own X% point against the frame's X% point, and magnifying about `transform-origin: X%` leaves exactly that point where it was, so one expression describes both the drawing and the magnifying and `pictureBox` stays in step with what the browser renders instead of approximating it. Only `cover` is aimed or magnified, because it is the only fit with picture left over outside the frame; `contain` is centred whatever the stored focus says, which is what lets a focus survive a trip through it and back to a crop.

The homepage keeps the village itself — the clock, the town map, the villagers, the noticeboard and the conversation — with only a **Menu** button and **Look again**. ### Homes and buildings

A home is a pin on the map, an occupant, and a **building**. The building is not a name the player writes: it is one of the kinds in `HOME_BUILDINGS` in `services/villages/prompt-preset.ts`, each carrying the class it belongs to, and there is exactly one kind today — `small-home`, a **Small home** in the **housing** class. The catalogue travels to the client on the snapshot as `settings.homeBuildings`, alongside `settings.defaultHomeBuilding`, which is the kind a newly dropped pin is drawn as, so the tab offers nothing the server did not name. A kind the server does not know is refused with a `400` on save, and one an older document carries falls back to the default rather than costing the player the house.

A villager lives in one home at a time. The server enforces it — `parseHomes` refuses a save that gives one character two houses — and the tab makes it unpickable: a row's villager chooser disables anyone who is already housed elsewhere and says so in the option's own words. Adding a second building later is a line in the catalogue and a class on it, which is what the `category` field is for.

- A `home-browser-tab` contribution, so Home gains a **Villages** destination with its own label, accessibility label, and tab icon.
- A privileged route group at `/api/villages`, registered through the host's revocable route slots so uninstalling takes it down again.
- A client bundle that defines the `marinara-capability-villages` element and draws the whole village itself: a picker over your character library, the villagers living here, one conversation per villager, and the settings panel.
- A village record and one transcript per villager, both kept in the Engine's package document store. The dialogue is the package's own — it never reads or writes an Engine chat, and it talks through the agent's own assigned connection.

### How a villager is written

A villager's turn is built out of two things that belong to two different people. **How somebody here talks** is the player's own Engine preset, read out of the Engine and assembled through its pipeline. **What somebody here knows** is the village's own knowledge box, because no preset can hold the weather, the roster, the noticeboard or what this villager was doing ten minutes ago.

**The preset is the player's.** Villages reads the Engine's own preset list and lets you pick one — the same rows, and the same `GET /api/prompts/:id/full` document an Engine chat would assemble. Your sections, in your order, with your wrap format; your markers, expanding out of the character card, your **Persona**, the transcript and the village's knowledge; your generation parameters; and your choice questions. The **Tense**, **POV** and **SNF/NSFW** toggles the Engine's own default preset carries are exactly this mechanism, and here they are put to you **once per village** and re-applied on every narration turn. A question you have not answered falls back to the preset's own stored value and then to its first option, so a preset you have already configured in the Engine arrives configured here.

**The knowledge box is the village's.** It is what a villager here knows about the current day, roster and noticeboard. It is stored on the village record, edited from **Menu → Village Settings**, and rendered fresh for every reply. Villages also reads the enabled entries of the Engine lorebooks selected for this village. Constant and context-matched entries are bounded and treated as background facts; the village setting and adopted cards remain authoritative. The `lorebook`, `world_info_before` and `world_info_after` markers expand the knowledge box and selected excerpts, with the excerpts included only once even when a preset has several lore markers.

**Narration turns are the ones the preset writes.** A reply, a greeting, a goodbye, and the acknowledgement of something you did, all go through it. The village's other work — the tick that writes the happenings, the judge that rules on a wish, the distill that summarises a conversation, the agenda that gives somebody something to wish for, the setup wizard — keeps its own prompts, because those are the package doing a job rather than a character speaking.

The default knowledge wording, the macro list and the box's cap — `VILLAGES_PROMPT_BOX_MAX_LENGTH` — all live in `services/villages/prompt-preset.ts` and travel to the client on the snapshot, together with the built-in fallback preset. The tab restates none of them, so it cannot drift from what the server renders. The cap is applied when the prompt is **rendered** as well as when the settings route is written to, so a hand-edited document cannot slip past it.

**Reading and assembling are two modules.** `services/villages/narration-preset.ts` reads the document over the Engine's loopback API — the same door the spin-off lane has used since 0.4.43, which is why no new permission is asked for — and coerces it back out of three raw rows' worth of undos: parameters, section order and variable values arrive as JSON **strings**, `enabled` arrives as a real boolean from the by-id route and as `"true"` from the Engine's own assembly path, and a marker whose config will not parse costs that one marker rather than the whole preset. `services/villages/narration-prompt.ts` then builds a turn through the Engine's own phases, in the Engine's own order: sections in the player's order, groups wrapped, neighbours merged, the leading system block squashed, depth sections injected at their depth, roles folded to what a strict provider will accept, and a single-user-message mode for models that want one. The order is the whole value of that pass, which is why the order was ported rather than approximated.

Two things are deliberately different from the Engine. Macros are resolved in one pass out of a plain map, because the Engine's macro engine is a server-private module a package cannot import; a token nothing knows is left as written, so a typo is visible rather than silently deleting a line, and a preset's own choice variables resolve through the same pass as the village's macros. And a preset with no `chat_history` marker still gets its transcript, appended to the prompt block — the Engine would send the preset without it, and a villager who cannot see your last sentence answers a question that was never asked.

**The preset decides the reply cap, unless the village does.** Narration replies are capped at `NARRATION_MAX_TOKENS`, 4096 — the Engine's own default, and the first number here that was not sized for a village that guesses — and the tab carries a switch that hands the cap back to the preset's own `maxTokens` instead. Temperature is adopted from the preset either way, as are its reasoning effort and verbosity where the package's model host can express them; anything it cannot express is dropped rather than approximated. The number is sent with every narration turn, so a change takes effect on the next sentence rather than on the next restart.

**The tokens are seventeen, and the knowledge box takes any of them.** A preset resolves through the same single pass, so a preset that writes `{{village}}` or `{{time}}` in a section of its own gets the village's name and the village's clock. The shipped knowledge default leans on the whole blocks and leaves `{{char}}`, `{{user}}` and `{{userDescription}}` alone, because a rule about how one person talks to another belongs in the preset.

| Macro                                   | Renders                                                                                                                                                                                                                                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `{{char}}`                              | The villager being written to.                                                                                                                                                                                                                                                             |
| `{{village}}`                           | The village's name.                                                                                                                                                                                                                                                                        |
| `{{user}}` / `{{userDescription}}`      | What the villagers call you, and what they already know about you.                                                                                                                                                                                                                         |
| `{{time}}` / `{{weather}}`              | For example `morning on day 1 of Spring`, and the weather in lower case.                                                                                                                                                                                                                   |
| `{{player}}`, `{{roster}}`, `{{homes}}` | Whole blocks. Each one renders nothing at all when its source is empty, so a village with no named player and one resident produces exactly the prompt it produced before these channels existed. `{{homes}}` lists one line per **occupied** home only, saying what building each one is. |
| `{{wishes}}`                            | What this villager privately wishes for, each with the small ordinary thing that gives it away. Renders nothing at all when the village has not written an agenda for them yet, which is the common case.                                                                                  |
| `{{noticeboard}}`, `{{lore}}`           | The same rule. `{{lore}}` renders selected, relevant live Engine lorebook entries, or nothing when no entries match.                                                                                                                                                                       |

`{{user}}`, `{{userDescription}}` and `{{player}}` are one answer read three ways: who you are. A linked Persona supplies it — its display name, and its description with appearance, personality and backstory attached in labelled paragraphs — and the hand-written name and description supply it while nothing is linked. Everything downstream reads the resolved answer and never the two fields, which is why the name a villager uses in the roster, on the map and in the prompt is always the same one.

**The fallback is by the box.** A village that has written nothing falls back to the shipped knowledge wording, which is what lets an improvement to the default reach a village that has never opened this panel. A village that has written something gets exactly what it wrote: a default quietly joined on behind it would be the panel putting words in the player's mouth about what their villagers know. An unknown macro is left as written, so a typo is visible rather than silently deleting a line, and substitution happens in a single pass — a substituted value is never rescanned for further macros. The old **How everyone talks** text is not carried anywhere: a rule about register is the preset's job now, and moving somebody's paragraph into a preset this package does not own would be rewriting their Engine for them.

Two areas of **Village Settings** are deliberately switched off and left on screen: **What this place is like** and **Places in the village**. They are one question with two halves and are moving to a setup flow of their own, and until that lands they are read-only rather than editable from two screens at once. The values still reach the villagers through `{{setting}}` and `{{venues}}`, and are still saved with the rest of the panel.

The narration preset is **village-wide**. Per-villager presets are not implemented, and neither is a per-villager knowledge box. Changing the preset clears the answers you gave to the previous one's questions, because an answer about Tense is an answer about the questions that preset asked.

## Art

`artwork/agent-covers/villages.png` and `packages/villages/villages-icon.png` are deterministic placeholders drawn by `build/cover.mjs` — a golden-hour hamlet for the catalog cover and a simplified mark for the tab. Both are exactly 512×512, which is what [the catalog validator](../../scripts/validate-catalog.mjs) enforces for covers. Replace them with real artwork whenever the art direction lands; only the size is load-bearing.

Villages does not ship a town-map image. Founding can generate one through the configured Engine image connection, accept a player upload, or keep the logical map image-free.

`src/engine/` mirrors the Engine's own paths: at build time the builder copies the vendored Engine source into a temporary directory and overlays this tree on top, so `packages/client/src/villages-package-entry.tsx` lands next to the Engine's client sources and can import them by relative path.

`manifest.json`, `agents.json`, `client.js`, `server.mjs`, and `locales/en.json` are **generated outputs**. Change the source or the build scripts, then rebuild — never hand-edit them.

## Rebuilding

```bash
node packages/villages/build/cover.mjs        # only when the placeholder art changes
node scripts/build-feature-packages.mjs villages
```

The second command bundles `server.mjs` and `client.js`, writes the manifest, `agents.json`, and `locales/en.json`, and produces a deterministic store-only zip under `artifacts/` named for the manifest version. Set `MARINARA_ENGINE_ROOT` to the current Engine checkout to provide its `esbuild` and client dependencies.

Then run the repository checks:

```bash
npm run check
node scripts/test-catalog-lanes.mjs
node scripts/validate-package-locales.mjs
node scripts/validate-catalog.mjs
```

Because `villages` is listed in `scripts/catalog-incomplete.mjs`, the builder keeps it out of every published catalog lane, so the catalog counts and the package guidance tables stay unchanged while it is being built. Delete the id from that set and rebuild the catalog when it graduates.
