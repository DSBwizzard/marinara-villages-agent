# Locations and Venue admission

Location is the umbrella for playable destinations. Venue is a status admitting a Location to village mechanics. Building a new structure still uses a New Venue Project. Saying that a new building exists cannot complete construction or supply Project resources.

The full-width **Locations** directory includes Venues and other known destinations. Only Venues have a status badge. Search and map/category filters apply before A–Z pagination; counts include only known, enabled records matching the search and map. **All** groups Venues before other Locations, and either category can use the whole list. Previous/Next show 50 results per page. Desktop and mobile use one scrolling page with a reachable pager. Returning from details preserves search, filters, page and scroll; **Map** opens the separate village map. Search and browsing make no model request. Narrative Locations open the same illustrated About and Zones screen as Venues. Management, editing and artwork generation controls remain available only for Venues; browsing retains the server-filtered known Zone details. The About description appears once, and identical Entrance text is omitted. Players can learn about Locations through ordinary Scene exchanges, selected lore and explicit **Explore**. The current GM Scene exchange validates up to two grounded introductions per reply. Reports stay unverified. Known locations are reused; private knowledge remains individual. One **Explore** action discovers a Location unknown to the player, or reports that no new Location was found, without moving the player. An existing unknown Location retains its identity, layout and supporting characters when discovered. Known Locations and all Venues are excluded by server checks; duplicate names on the same map reuse a supplied unknown identity or yield no new result. Concurrent discoveries recheck knowledge before publication, while replaying a completed request retains its original result. Blank input explores nearby; a creature or object alone is not a Location. **Visit** decides one or two Classes from the Location’s existing use and handles any unfinished first-arrival preparation before ordinary Scene entry, with up to six Zones besides Entrance and up to four relevant supporting identities. Returning reuses the saved location and layout. A failed or unusable generation retries once automatically. Exploration then quietly returns to idle; failed entry retains the known destination. The player has no saved discovery request, Retry or Dismiss controls. Internal receipts prevent duplicate calls and publication; refresh and browsing do not generate replacements.

Locations reuse Scene entry, Zone navigation, connections, access, acoustic witnesses and playback. NPC associations do not imply presence. An observed arrival must be proposed in the current GM exchange and validated against admitted positions; it cannot hear earlier conversation. Supporting characters retain compact identities, scoped associations, availability and native Memories. They have no Villager relationship scores, Agendas, autonomous activity, employment, Wishes or construction leadership. A reply has at most four responding people. NPCs and the player consume no Villager occupancy slots.

A Location can host ordinary activity and retain supported nonstructural changes to its rooms. Controllers can issue entry permission or consent within their recorded scope. Authority comes from the saved controller record.

After an admitted visit, **Add as Venue** admits the Location with its complete saved Class set and selects an ordinary map position. There is no admission Class picker. Prepared locations receive only a Class decision on their first Visit; their layout and supporting identities stay intact. Admission is one server transaction with current world, Location and map revisions, request replay protection and a capacity check. Conclude the current Scene first. A reported or unvisited destination cannot be admitted. Admission creates no Project, objectives, lead, deadline or pending capacity reservation. Actual structural work uses ordinary Renovation after admission; building a new structure uses a New Venue Project.

Promotion keeps the same location, Zone and supporting-character IDs, access and history. It adds eligibility for ordinary Venue mechanics without assigning ownership, jobs or housing, revealing private interiors or resetting conditions. Later Renovations still need scoped controllers' agreements.

The existing limits remain: 16 Venues across the whole Village, two active Projects (including paused work), and six drafts. Locations without Venue status consume no Venue slot. Admission consumes one immediately and counts outstanding construction reservations. No gameplay cap is imposed on stored Locations. The list returns 50 records per page. Narrative Locations have no separate map layer or marker editor; admitted Venues use the ordinary map controls. Prompts receive bounded relevant summaries, never the entire Location library.

Private Location/NPC records and source receipts use the existing immutable history pages and Village CAS. Supporting identity/availability, Location records and Memories are inspectable through REPAIR; corrections use its review, Undo and checkpoint flow. Disabling a record stops its future use. Existing Scenes retain their admitted sources and witnesses.

The current build requires a fresh format-20 Village. Older saves are rejected and their storage remains intact.
