# Villages architecture and compatibility

The 0.7.0 architecture baseline separated feature ownership, host access and saved-state projection. Its fresh-world scope was a historical release decision; it does not authorize loss or reset of later saved worlds.

## Code ownership

Maintained source is in `packages/villages/src`.

| Owner           | Responsibility                                                                |
| --------------- | ----------------------------------------------------------------------------- |
| Client features | Screens, feature state and commands                                           |
| Client shell    | Navigation, shared snapshots, responsive state, presence and feature assembly |
| Server entry    | Assembly and lifecycle of activation-owned services, adapters and jobs        |
| Server features | Request coordination through explicit contracts                               |
| Domain          | Saved models, decoding, calculations and rules without host I/O               |
| Adapters        | Engine public APIs, storage, generation, accounting and diagnostics           |
| Jobs            | Owned background work and finite preparation                                  |

`scripts/feature-interfaces.mjs` declares cross-feature contracts. Architecture checks enforce private feature boundaries, client/server privacy, dependency direction and absence of cycles. Shared support does not import shell assembly or private feature implementations. Public contracts expose consumed values and commands rather than another feature's private state or hook types.

New layers and interfaces need a concrete purpose. Tests import the actual owner rather than relying on forwarding exports.

## Activation and request lifetimes

Each activation owns its services, caches, queues, operation maps and host connections. Asynchronous work retains its originating owner. A missing or disposed activation cannot borrow another world's services, even when identifiers match. Cleanup from an older owner cannot stop or clear its replacement.

Client commands claim admission before mutation and preserve the originating world, selection and request identity. Results, errors and cleanup belong to that claim. Reset, disposal or replacement retires old work; functional acknowledgments preserve newer edits. These lifetimes do not impose global ordering on independent full-snapshot responses.

Cancellation revokes authority to apply late effects. It does not promise that an upstream provider physically stopped or that an uncertain request was unbilled. Existing operation deadlines, request reservations and recovery records remain authoritative.

See [activation dispatch ownership](activation-dispatch-ownership.md), [activation cleanup](activation-cleanup.md) and [Decisions ownership](decisions-activation-ownership.md).

## Scenes and privacy

A Venue contains Zones; a Scene continues across movement between those Zones. At admission, the server captures attendance, positions, activities, connections, time and source facts for writing. Background changes cannot rewrite an active snapshot. Exact accepted Scene effects extend its presentation context through existing receipts; those projections never become authority for a world write. Unseen attendance, captured facts and private contents stay server-side. Current-format Scenes reserve sparse memory continuity before attaching their captured facts; recovery reuses that reservation. Closed Scenes stay closed.

Source spans, witnesses, authority, revisions and physical receipts bind proposed effects to the saved interaction. Hearing, understanding, disclosure, entry and permission to change a space remain separate. Domain validation determines actual effects after model interpretation.

Ordinary snapshots expose only player-safe projections. Private diagnostics, raw provider output, frozen prompts and undiscovered interiors do not enter ordinary client contracts.

See [Scene privacy](scene-response-privacy.md), [System responsibilities](system-ownership.md) and [generation lifecycle](generation-pipeline.md) for the detailed contracts.

## Saved work and compatibility

The current runtime uses Village format 13, native Scene storage format 13 (logical Scene/continuity contract 3) and native relationship root format 4 (logical relationship contract 3). Scene turns store flat Wish proposals and one compact application authority independently of their complete frozen reinterpretation context. These storage changes require a fresh Village; unsupported records are rejected without conversion or writes. Existing saved data must remain in its independent storage with its matching runtime. There is no migration, history backfill, dual write or legacy reader. Compact CAS roots publish immutable history references with matching mechanics. Bounded pages hold Memories, active sparse memory preimages, relationship event receipts, per-edge records/experiences, per-thread complete letters and Scene transcript lines and submissions. One submission occupies one payload block so changing its recovery state does not rewrite neighbouring contexts. Current and admitted Scene snapshots own independent heads; readers remain admitted until their referenced pages have loaded. Publication remains admitted through owner CAS. Owner-aware idle housekeeping reclaims superseded immutable roots, pages, snapshots and retired Undo bodies; checkpoints share heads and transitive pages. Scene attachment is a separate resumable stage. See [Memories](memories-core.md).

Background jobs use response-storage format 3: a physical request claim precedes dispatch, and one immutable, opaque response body is published before its compact job reference. Normal and late replies share that path. Before Retry, replacement or obsolescence releases unfinished evidence, the existing background-history kind retains an exact, content-addressed native before-image under the same repair admission as the current-job CAS. Competing writes cannot overwrite a richer before-image, and a lost publication acknowledgement verifies the existing immutable bytes. Only positive proof from the live invocation can release a reservation that never entered its provider. Known optional results save against their original attempt before supersession checks; uncertain outcomes remain held. Successful effects release settled recovery payloads only with their exact durable World receipt; optional or required request uncertainty remains owned independently. Historical response selection, rejection accounting and receipt retirement remain part of the recovery lifecycle work.

Background activity, mail and social-recovery inputs, queued replacements, retained attempts and World outboxes store admission-format-1 resident directories with scoped immutable Wish heads. Original encounter, review and mail relationship baselines have separate heads; null means unavailable, distinct from a known-empty state. Ordinary reads retain native metadata, and selected execution or settlement hydrates only its required capture. Mutable request facts detach before asynchronous admission while verified history leaves remain shared. Publication derives protection from physical World/job identities, exact World setup and resident incarnations under full repair admission through the actual owner CAS acknowledgement. A source-job hint is re-read and checked before its references can protect a new World outbox. Unprotected references validate or rematerialize their complete dependency graph; cache contents grant no ownership. Checkpoints, available Undo, prepared repairs and proposed overlays retain these same typed heads. Cleanup traces their dependencies with the existing shared Wish and relationship tracers and completes validation before deleting anything. Comparison fingerprints own no data and avoid serializing complete captured history.

Both background replies and Scene operation-evidence format 3 retain a payload checksum, so a prospective publication claim can validate bytes before its completed owner reference exists. Recovery preserves deliberate retry holds and reuses saved replies; metadata-only usage previews load bodies only for an eligible recovery parser. Current jobs, retained attempts, prepared repairs and available Undo records validate their response dependencies. Scene response selectors retire only after normal Scene retirement has published its durable terminal, every dispatch has settled, and no current, checkpoint, Undo or prepared-repair source owns that Scene. A gathering's fixed prospective Scene ID also owns responses before its native Scene exists. Any retained Scene version conservatively keeps its selectors and purchased bodies; no age or count limit applies. Idle cleanup validates all owners and physical terminal/Scene identities before removing selectors, then sweeps unreferenced bodies. Interrupted deletion leaves bodies available, and late callbacks require their exact saved claim under full repair admission before publication, so they cannot recreate retired allocations. The existing terminal supplies replay protection; no second tombstone lifecycle is introduced. Background bodies enter the same validated sweep only after every current, historical, available Undo and proposed-repair owner has been traced. Background publication checks its exact durable physical claim under full repair admission; ordinary replies read only their current slot, while late replies may scan retained attempts. Retiring the last owner therefore prevents an old callback from recreating a collected body. Current compact receipts and unfinished historical ownership remain independent of body cleanup.

Live residents and departure captures own compact Wish collection heads. Each Wish header owns separate condition and history trees; changing its current state or appending evidence shares older immutable pages. Ordinary authority reads leave nonempty libraries unloaded, and Wish consumers explicitly request their actors. The live owner's working layout is retained; historical layouts have an eight-head, 4 MiB cache bound. Removing a resident adds their last committed head to the world's paged private archive, which has no expiry. Re-admission starts a new current library without deleting the archive; restoration preserves this monotonic archive. Checkpoints, available Undo and prepared repairs retain their exact transitive dependencies. Cleanup validates every owner before deletion and shares page validation across retained versions; publication and reads use the existing repair admission gate through owner acknowledgement. Frozen Scenes and their admitted snapshots retain each resident's exact canonical Wish head. World and the single active Scene, including its admitted snapshot, retain separate working-layout leases; replacing either owner group preserves the other, while archived layouts retain the bounded historical cache. Captured bodies remain immutable through logical cloning and Scene change detection. Closed transcript reads hydrate their transcript and saved turn mechanics without loading private frozen Wish libraries. World Wish effect receipts own single-Wish canonical heads, sharing condition/history pages with the just-published resident library. Metadata reads leave after-images unloaded. Scene readers select the last effect per Wish in transcript order, including delayed completion, instead of loading every historical version; an unavailable required after-image blocks Wish context rather than exposing a stale baseline. Cloning shares immutable after-images. Reusing a reference from a checkpoint or Undo outside the previous live owner requires physical transitive validation under the full repair admission before publication. All retained and proposed repair sources trace effect heads as well as resident, departure, archive and frozen Scene heads. Scene submissions and writing/parsed checkpoint packets retain clone-safe canonical Wish references, scoped to their Scene, World and captured resident incarnation. Default history reads leave these packets compact; writing replay and Wish Retry explicitly resolve the selected exact capture before model work. Pending checkpoint claims, completed or abandoned operations, admitted snapshots, checkpoints, Undo and proposed repairs protect their transitive pages. Missing dependencies or invalid captured owners stop recovery and hold cleanup. One working full capture per actor and one selected effect per Wish may share the existing active Scene cache; actual native owners independently authorize reuse, and archived reads cannot replace these working slots. This cache is disabled during repair simulation and grants no cleanup ownership. Background Wish inputs still need their separate reference conversion. Ordinary effect publication shares pages; receipt metadata, cold context loading and the remaining context/pagination work still need their complete gameplay scaling validation.

Saved generation, validation, committed effects and Scene bookkeeping are distinct stages. Claims precede provider dispatch; completed responses and effect receipts support local replay. Compare-and-swap retries reuse saved output and preserve request accounting.

Jobs and operations bind the village seed, subject, source revision, attempt and admitted contract. Reset, removed residents, changed inputs, supersession and teardown fence late effects. Existing operations retain their original prompts and stage contracts rather than silently adopting new generation behavior.

Reads, polling, notices, diagnostics and storage retries do not authorize paid dispatch. Unknown provider outcomes require deliberate retry. A successful model response does not by itself establish a committed effect.

Engine document writes are buffered, without a package-visible durable flush barrier. A hard crash can lose recently acknowledged claims or responses. Recovery records improve normal-operation replay; they do not provide crash-proof billing deduplication.

Zone.description is the authoritative current physical account, bounded at 4,000 characters. Zone.state carries only a monotonic revision, updatedAt and one optional recent paragraph (600 characters, occurrence plus 24-hour expiry). Natural updates use unique exact text edits and/or an addition, reject overlapping/ambiguous anchors and overflow, and preserve all text outside edits. System judges meaning, available supplies and consent; code binds actions and consent to witnessed sources, then enforces current authority and revisions. Memories retain knowledge and intentions rather than duplicating physical truth. Scene receipt replay uses exact accepted after-values against frozen context. REPAIR and checkpoint undo restore exact retained expiry, advance revisions and retain the existing Project design hash, which includes descriptions only for deliberate replacement targets. Artwork uses enduring prose, with a bounded 8,000-character input and the existing compiled-style guard. Temporary use requires current access; enduring changes require current-controller action or witnessed consent. Scheduled resident encounters settle physical proof before dependent Memories, with actor-only witness audiences. Catch-up stages all effects atomically. Full physical after-values remain only while their source needs replay, then retirement retains compact outcome identities. Uncommitted failed encounters can be skipped; partially committed encounters must finish recovery.

Saved-data changes preserve existing worlds or explicitly document the compatibility decision. The 0.7.0 fresh-world baseline and later feature-specific draft resets are not standing permission to discard data.

The user-approved storage growth and recovery overhaul is a one-time exception: its PRs may change saved formats and require fresh Villages, including between PRs. Do not add migrations, legacy readers, transitional adapters or cross-PR save compatibility. Each supported format must persist and recover correctly across restarts. This exception does not authorize resetting or replacing an existing installation or world; deployment protections and recovery holds still apply. After the overhaul, saved-world compatibility is again the default recommendation.

### Recovery disposition

Scheduling labels and failure messages do not establish that evidence is disposable. The domain recovery classification checks saved work and uncertainty before accepting a terminal label:

| Disposition      | Required evidence and behavior                                                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pending          | Accepted work is queued, running or paused. Retain its admission and continuation; an explicit pause does not authorize dispatch.                                       |
| Recoverable      | A saved reply, result or partially committed effect permits useful continuation. Reuse purchased output before considering a replacement request.                       |
| Uncertain        | A dispatched request, effect or publication has no conclusive outcome. Retain its reconciliation evidence and replay guards; do not automatically purchase a duplicate. |
| Completed        | Required effects and publication are acknowledged and no continuation remains. An inconsistent completed label cannot override retained unfinished evidence.            |
| Failed           | The attempt ended conclusively without saved work or an unresolved obligation. Ordinary diagnostics can eventually be retired independently of replay protection.       |
| Safely abandoned | Dispatch/callback authority is fenced and committed effects reconciled. An obsolete label alone does not prove this disposition.                                        |

Explicitly abandoning an uncommitted Scene request preserves its exact input, responses and accounting evidence, but releases its inactive Scene snapshot. Close recovery uses the current Scene; earlier checkpoints and Undo records own their original snapshots independently.

Compaction requires a terminal disposition, preserved accounting/replay protection and an owner for every still-needed piece of evidence. Full receipt deletion additionally requires a durable closed scope, epoch or high-water rule that rejects every possible replay, and no remaining reference. Age, a failure label and diagnostic retention limits are insufficient. These requirements precede the later compaction implementation; the current background cleanup only adds a guard against discarding pending, recoverable or uncertain records. It does not enable new pruning or paid retries.

An explicit Village Reset ends the old world's ownership and retains the established removal of its private jobs after active work settles. The new seed fences their application to the replacement world. Removing a resident or marking a current-world job obsolete does not confer that authority. Malformed records whose ownership cannot be established remain protected. Unknown token counts are accounting uncertainty, not proof that a completed request is still unfinished.

Unapplied REPAIR reviews are administrative previews produced by simulation. They have no committed effects and are never the sole owner of a paid response: their authoritative source records remain unchanged. Keep at most ten valid current-world previews, discard them on explicit cancellation, and retire an applied preview in the same journal as its effects and acknowledgment. Apply checks the retained preview and its unique creation token before publishing any effects. A repeated request may recreate an evicted/cancelled review, but its new token cannot restore an old Apply's authority or let a late Cancel erase the replacement. Drafts remain client-owned. Unfinished repair journals recover before cache retirement; unknown/corrupt or foreign ownership is retained. This cache limit does not prune player history, Undo or checkpoints.

### Reference lifetime

Ownership is explicit and world-scoped. Do not infer references by scanning arbitrary player/model prose. Current storage uses existing payload intents, operation records and captured facts; later storage changes must preserve these owner obligations before adding deletion:

| Owner                                             | Protected dependencies and release boundary                                                                                                                                                                                                                  |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Current authority and meaningful retained history | Current facts, exact evidence, individual knowers, corrections, resolutions and Forget suppression. No automatic history expiration or lifetime cap.                                                                                                         |
| Active/frozen Scene                               | Captured attendance, privacy, facts, accepted own effects, evidence and media. Release only after established retirement and transfer of retained evidence ownership.                                                                                        |
| Departure capture and unfinished catch-up         | Exact historical facts, admissions and unsettled outcomes. Release after settlement or proven safe abandonment; retained outcomes remain owned by history.                                                                                                   |
| Unfinished or uncertain operation                 | Admission, saved paid replies, commit/publication evidence and assets. Release only after reconciliation and terminal disposition.                                                                                                                           |
| Available repair Undo                             | Exact inverse dependencies and assets. Retain the ten most recently committed successful repair payloads; consumed Undo does not resurrect older payloads. Permanent repair headers preserve changes, audiences and Undo provenance after availability ends. |
| Automatic/manual checkpoint                       | The complete transitive snapshot and media dependencies. Retain ten automatic checkpoints by committed publication order; manual checkpoints remain until explicitly deleted. Recovery/explicit holds override ordinary eviction.                            |
| Saved evidence and replay protection              | Exact cited sources and information that rejects duplicate effects. Release only after ownership transfer or a proven replay fence with no remaining reference.                                                                                              |

Publication protects existing and proposed dependencies before creating bodies, validates them, then publishes through the existing CAS/repair fence. Ambiguous or interrupted publication retains its intent. Cleanup may release superseded data only after new ownership commits, and must recheck owner revisions and outstanding intents under the same fence before deletion. A writer cannot attach a new reference concurrently with that deletion. Missing, corrupt or unknown ownership defers cleanup. Restore validates/protects its dependencies before publication and cannot rewind operation epochs or replay protection. Startup reconciles unfinished publication/repair journals before cleanup.

Checkpoint format 2 headers and separate Undo bodies reference content-addressed native document snapshots. Snapshot data remains identical to its source so Engine can see the same Gallery owners. Snapshot identity includes the complete source, including its saved clock. Configuration saves preserve the original setup identity. Plans and format-3 repair journals reference immutable after-images and before digests, with opaque packets only for validated create-only Memory pages. Application composes effects, retention ownership and plan retirement in one overlay and journal. Every replay frame and source is validated before the first effect. Preparation and owner publication remain admitted through the existing repair gate; cleanup cannot enter that gap. Deleting a manual checkpoint releases its references with one CAS and retains a minimal token tombstone so a delayed save cannot recreate it. Physical cleanup validates all retained owners, including other world scopes, before its first deletion. Each retained review has its own proposed-write overlay; virtual pages cannot validate a missing physical checkpoint dependency. The Memory tracer follows references inside serialized Scene headers and visits shared structural pages once per lookup scope. Malformed or missing ownership defers deletion. After all writers drain, well-formed abandoned intents can release partially created unowned artifacts.

Keep native media reference fields visible to Engine's Gallery protection even when historical prose is stored opaquely. Cleanup acts only on attributable Villages candidates. Avoid authoritative reference counts or a generalized collector: extend existing intents/fences and explicit owner manifests only where a concrete storage change requires them.

Storage admission is shared by canonical Engine backend identity across replacement module snapshots. Disposed activations retain their outstanding admission until invoked host writes settle; they cannot publish new work. Startup journal readiness is invalidated when the shared recovery epoch advances. Full history reads remain admitted across their entire load. Cleanup acquires the same exclusion before tracing and deletion; newly arriving gameplay waits for cleanup rather than receiving a repair conflict. Package installation still uses the guarded stopped-runtime boundary for the first deployment of this participation contract.

An exclusive repair operation validates existing history pages through one private, operation-local inventory, including its per-ID commit guards and journal recovery preflight. This avoids repeated Engine table scans without a persistent index or an extra global membership guard. Expected absence still requires an individual lookup to detect wrong-kind ID collisions. Staged writes override the physical inventory; physical page writes invalidate even an in-flight inventory after a lost acknowledgement. Returned records are detached, and the inventory ends with exclusion. Ordinary gameplay retains selective page reads. Administrative operations trade a full retained-page read and temporary memory for fewer table scans; new-page creation and other Engine storage costs remain separate.

One initial idle sweep recovers allocations from an earlier activation. Later sweeps are coalesced after approximately the greater of 1 MiB or the prior live footprint has been allocated. This footprint includes retained owner metadata and owned sprite bytes as well as immutable bodies, so many manual checkpoints do not cause increasingly frequent full owner scans. Estimates are activation-local and may safely overcount failed creates; no routine persistent counter writes or new scheduler are needed. Ordinary saves below that allocation budget do not scan retained history. Cleanup does not expire meaningful Memories, correspondence, Wishes, relationship or repair history, or remove manual checkpoint headers.

Each Sprite Manager upload claims a fresh, never-reused Villages UUID path before writing, with its exact filename, digest and byte count; a separate acknowledgement precedes owner publication. Existing repair admission spans upload through the final World or setup-draft save. World, departure, both social outboxes, frozen/admitted Scenes, background current/replacement/history and setup drafts retain their typed artwork references; checkpoints, available Undo and proposed repairs retain their transitive sources. Removing artwork releases only the current assignment. The existing collector validates every retained owner before deleting an unowned attributable file, and retains its allocation until Engine acknowledges deletion. Image-serving 404 also covers corrupt files and is not deletion proof. Directory inventories are indexed once per asset per sweep. Uncertain uploads remain held for their entire Engine process, across package replacement; only a full process restart proves that producer has exited. Gallery images, Engine character originals and files without allocation records are outside automatic deletion. The managed UUID directories are private allocation namespaces, not general-purpose user libraries.

Media cleanup that encounters an unavailable Engine remains eligible for the next admitted idle event. Integrity failures retain allocation backoff; neither path starts a retry timer.

See [response recovery](scene-response-recovery.md), [Scene continuity recovery](scene-continuity-recovery.md) and the [generation lifecycle](generation-pipeline.md).

Relationship format 3 retains exact event updates and independent Scene/live predecessor revisions. It never embeds a growing predecessor edge in each receipt. Identical Scene/live updates share one stored patch; applying it to different predecessors still preserves their distinct histories. Both Scene views admit only their own retained submission IDs, order events by the relationship publication sequence, validate complete predecessor chains, and apply updates to one detached captured view. Missing or forked predecessors hold recovery before any patch is applied. Inherited records, individual knowers, exact evidence and shared terms remain intact. Checkpoint restoration and Undo cannot rewind the publication sequence; their live revision increases do not rewrite frozen Scene predecessors. Old or wrong-world relationship records fail closed without conversion.

Relationship root format 4 owns a content-addressed private manifest in the seed/setup namespace. It reuses the existing immutable history-page codec and physical page kind. Separate trees for each edge's records/experiences and each thread's messages prevent a single long pair or correspondence from becoming one growing leaf. A bounded four-head decoded cache supports alternating current and historical reads; only mutable containers detach, and historical leaves stay immutable. Publication reuses a cached layout only when a current native owner still protects it. A stale unowned cache entry must rematerialize every dependency before publication. Root identity, payload digest, page identity, ordered list keys and nested headers are validated; missing or foreign ownership holds cleanup before deletion. Checkpoints, available Undo and proposed repair overlays trace the same nested trees. Recovery replay never treats cache contents as persisted authority.

Native Scenes store their captured relationship head and seed/setup scope, including the exact admitted Scene inside an unfinished operation. Hydration returns the verified canonical immutable value. Only that exact value can retain an associated head; publication reuses it only while the previous native Scene still owns it. New or changed captures prepare the actual logical value, including any reconciled facts, rather than substituting the current live head. The coordinator keeps its admitted snapshot compact; its consumer explicitly hydrates that saved snapshot. Pure logical decoding rejects unhydrated native references, and metadata-only listing/backlog reads cannot access unloaded continuity.

Scene presentation detaches mutable relationship containers for replay while immutable history leaves remain shared. Scene change detection compares the remaining saved fields and immutable body identity without serializing the body. Native ownership checks bind row IDs, Scene IDs, Village seeds and captured scopes before admission or publication. Checkpoints validate all transitive Scene pages with the existing structural tracer before publishing or restoring them; collector marking includes current and checkpoint/Undo/review versions with separate proposed-write overlays. Missing ownership holds every deletion. Native Venue/media fields remain visible to Engine.

Scene storage format 13 publishes separate typed, counted transcript and submission trees directly in both the current Scene and its admitted snapshot. The two collections share page publication, bounded caches and tracing, with distinct namespaces. The existing immutable page codec bounds blocks and text chunks; submission blocks contain one turn so a recovery update rewrites only that turn. Verified immutable leaves retain their identity across ordinary saves and participant joins. Submission edits detach the selected turn and its nested state; returned arrays cannot mutate cached history. Recorded staging, look and physical-position identities must remain in the captured participant directory; witnesses and sound-only hearers may be outside that cast. Hearing is derived from each exact line's audience and sound-only projection. A separate public History index stores only eligible line identities, positions and public-output digests; it never duplicates prose. Metadata reads throw if asked for unloaded transcript, submissions or continuity. Recovery explicitly loads submission mechanics; archive and saved-evidence readers use the same bounded transcript/submission caches.

Scene operation responses and completed checkpoint values have separate immutable bodies. Each reference binds the Scene, Village seed, logical operation, frozen input/revision and checkpoint or attempt key. The current operation owns its admitted Scene snapshot; that snapshot cannot contain another operation. Logical operation contexts hydrate exact values without changing synchronous checkpoint access. These stage values contain text, domain IDs and evidence, not independently allocated media: the typed World and Scene records own actual media. A fixed prefix makes each serialized JSON envelope opaque to Engine reference traversal, including large Wish baselines and prose resembling asset IDs. An envelope distinguishes an undefined result from null and an absent result reference. Publication checks the exact payload digest and immutable document identity. This bounds ordinary native operation writes and warm serialization; it does not yet eliminate large logical Wish contexts or the bytes required to publish a new stage value.

Physical dispatch claims precede model work. Normal and late replies use the same signature-keyed Scene receipt and an atomically published body before Scene adoption. Rejection fences the exact selected physical response, independently of the logical retry that adopted it; older callbacks cannot select a replacement after that fence. Local checkpoint claims similarly precede stage work and protect a prospective body across failed acknowledgements. Recovery adopts an already saved parsed value rather than recomputing it. Writing-completion checkpoints only return the independently retained raw response and share that body. Cleanup follows current operations, explicitly retained abandoned operations, checkpoint/Undo/review versions, selected receipts and unfinished publication claims. Missing or malformed ownership holds every deletion. Scene retirement does not delete response receipts: a checkpoint made before the response arrived can still restore its earlier request. Receipt retirement requires its separate closed-scope proof.

Full work admission covers page allocation through the Scene CAS. A drained cleanup therefore sees either a complete native owner or abandoned, unowned pages; this path needs no separate publication-intent record. Cache entries alone cannot establish ownership or publish missing dependencies. Checkpoint and cleanup passes validate each shared block once, including canonical line shape, counts, duplicate IDs and cast dependencies, under separate proposed-write overlays. Retirement validates the authored source before logical coercion. Submissions and model context construction remain separate costs; transcript sharing alone does not bound a complete Scene request or all Scene persistence.

Departure captures own one exact relationship head at `returnCatchup.capture.world.relationshipHead`, bound to the containing Village's seed and setup stamp. Repository reads hydrate this explicit owner through the same admitted backend as its World CAS; pure logical decoding rejects unhydrated references. Calendar, resident, narrative and Project projections clone mutable facts while sharing verified immutable departure history. Checkpoints, available Undo records and unfinished repair overlays retain these heads and their pages even after the active capture is removed. Restoration still discards the active absence capture; retained checkpoints continue to own their saved capture. Missing or malformed ownership blocks publication, restoration and cleanup before deletion.

Resident catch-up job inputs and capture fences use exact comparison fingerprints, including the full world namespace. They are not owning references and never hydrate or publish history. Fingerprints reuse the existing page layout and hash the actual reconciled logical value; a live head or event counter alone cannot describe changed permissions. Unknown context remains distinct from a known empty ledger and cannot authorize resident work. Bounded captured-relationship writes alone do not establish bounded gameplay requests. Social encounter and meeting history has no automatic lifetime limit.

Mailbox responses contain at most 50 letter summaries and an independently pageable set of at most 50 recovery entries. Their row budgets are 64 KiB and 16 KiB respectively. Exact bodies are fetched individually; unread incoming previews and unseen purchased outbox replies are not exposed. Deterministic position cursors are scoped to the Village, folder and clock projection without owning or pinning history. Current requests index jobs, pending errors and message identities once rather than scanning the complete mailbox for every row. This bounds response/rendering/serialization work; it does not make cold relationship hydration, metadata scans or existing outbox settlement an indexed backend query.

The public snapshot and correspondence responses carry an opaque seed/setup scope. Letter summaries/details additionally carry a computed fingerprint of content, source identity and accepted disclosures, excluding read/status/error fields. Detail, Read and Retry require the selected fingerprint: checkpoint restoration can rewind the request-ID directory while retaining the same Village scope. Read still publishes the complete permitted disclosure evidence before acknowledging readAt, without model work. Commands and shared outbox settlement take existing work admission and authority ownership before consulting shared tasks. The client keeps one selected body independently from index pages, rejects stale query/detail/command responses, retains scope-bound drafts/request identities and follows existing snapshot updates without a dedicated settled Mailbox timer.

The Scene History drawer uses a separate read-only endpoint with at most 40 public entries and a 128 KiB response budget, preserving one oversized exact entry whole. Older/Newer replace the displayed page. The endpoint seeks the public index and selected transcript blocks without hydrating frozen context, submissions or the complete transcript. Cursors bind Village scope, Scene and a digest of ordered public output; hidden-only changes leave them valid, while changed or restored public output requires refresh. Neither private offsets nor private source heads enter responses. The current and admitted Scene owners publish the index atomically with their source heads under existing work admission. Checkpoints, Undo and repair overlays trace the same index; missing ownership blocks cleanup. Coordinator timing saves rebind the index source within the same CAS; changes to effective hearing rebuild it before publication, while admitted snapshots keep their independent captured index. Ordinary operation checkpoints do not reread transcript prose. Range reads stay admitted until their response is constructed. Active and command Scene responses also carry a bounded playback window of complete main/aside moments. Each moment references its existing prose and immutable first/last paragraph presentation (visible poses and desktop/phone placement), without copying the encountered cast into every frame. A single current staging accumulator continues publication; initial staging identities are captured once. Moment counts and paragraph prefixes support exact global reading counters. Playback cursors bind the exact public anchor and remain valid across appends; changed or restored anchors require an explicit refresh. A separate cancellable client lane cannot replace current Scene authority. Scoped line/paragraph bookmarks preserve older reading positions; a reply larger than a window backfills its first unread passage. One recently closed playback owner in the existing active-venue pointer keeps the final Scene readable across navigation/restart, until a new native Scene and its pointer commit or Reset removes it. Missing or foreign closed ownership holds cleanup and restoration. Close acknowledgements include the latest exchange; the existing changes feed drains any older recovered notices in bounded pages. These bounds concern history-dependent response and rendering work; full private Scene hydration, context preparation and the encountered participant header still have separately measured costs.

## Engine and validation

Villages uses declared permissions and public Engine APIs. Optional Decisions integration feature-detects `api.runtime.decisions.evaluate()`; unsupported capabilities retain System behavior. Private Engine implementations are not bundled.

Locked dependencies and pinned public declarations support builds without an Engine checkout. The repository builder owns generated payloads and deterministic archives; maintained source, tests and documentation are committed.

[DEVELOPMENT.md](../DEVELOPMENT.md) owns commands and release steps; [AGENTS.md](../AGENTS.md) owns development principles. Provider-free tests establish their exercised contracts, not live-provider quality or actual Engine integration.

The former extraction ledger is retained in Git history. This document describes the resulting boundaries rather than intermediate task status.
